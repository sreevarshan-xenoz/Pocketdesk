# Security

Pocketdesk lets a phone see and control a computer, so what it protects, and what it does not yet protect, matters more than its feature list. This page describes the design as it is in this tree, including its limits.

**Two things to know before you pair.** Pair by scanning the desktop app's QR code: typing an address, or picking a computer found on the network, trusts whatever answers there first (limit 1 below). And the internet path is on by default: relays see both ends' IP addresses, which endpoints talk and how much, and the Mainline DHT links the computer's WAN id to its home IP, and the phone's IP to the id it looks for (limit 4), unless `dht_publish = "off"`. None of it needs a port forward, except waking a sleeping computer from outside and running your own relay. "Reachable from the internet" in the desktop's Settings (`internet_path = false`) turns the whole path off: no relay or DHT is contacted, phones reach the computer on the same network or through Tailscale only, and your other computers do not link with it.

## Reporting a vulnerability

Please report security problems privately. Use GitHub's **Security → Report a vulnerability** on this repository, which opens a private advisory only the maintainer can see. Do not open a public issue. Include what you found, how to reproduce it, and what an attacker gains.

## The connections and what protects them

| Connection | Port | Encrypted | How the peer is identified |
|---|---|---|---|
| Control channel (pairing, clipboard, file browse, notifications, commands) | TCP 1716 | Yes (TLS 1.3) | Both ways by key, as on the stream: the phone pins the desktop's certificate, and must present its own, which the desktop holds the device to (device keys). A client that does not speak TLS is refused |
| Video, audio and input stream (LAN) | UDP 4716 (QUIC) | Yes (TLS 1.3) | Both ways by key: the phone pins the desktop's certificate (first use, or the QR code's fingerprint) and checks the handshake signature; the phone presents its own certificate, and the desktop holds the device to it (device keys) |
| Stream over the internet (WAN) | iroh (QUIC) | Yes | Both ends' iroh keys; the desktop holds the phone to the iroh key it registered on the LAN |
| Control channel over the internet, when TCP 1716 cannot be reached | iroh (QUIC) | Yes | Both ends' iroh keys. Only a paired phone whose iroh key was registered on the LAN; nothing pairs over it. Another of your computers dials it with its own ALPN, `pocketdesk-computer/1`, which only picks the congestion controller: it is held to the same keys and checks, and is let in no further. File transfers ride streams the computer opens on it (`internet_files`, on by default), held to the same keys, with no TLS layer of ours and no connection back to the phone |
| File transfers | a fresh TCP port per file | Yes (TLS 1.3) | Each end accepts exactly one certificate: the phone, the desktop it pinned for the address it asked; the desktop, the key bound to the phone that asked. A one-time key per transfer is checked inside, and the desktop dials only the address the request came from |

Tailscale, when you use it, wraps all of these in WireGuard, which encrypts and authenticates the whole path between your devices.

## What is protected

- **Pairing:**
  - A 6-digit PIN is valid for 5 minutes and pairs one phone. A PIN that paired stays spent even if its file cannot be deleted, and a PIN file without its minting time is no PIN.
  - It is discarded after 5 wrong guesses, and the desktop shows at most one new PIN every 10 seconds.
  - It travels inside TLS. With the QR code, the phone checks the desktop's certificate before the first byte, so the PIN reaches only that computer.
  - With `pairing_required = true` (the default), an unpaired device may only pair, on the control channel, and is refused on the stream.
- **The desktop's identity:**
  - The phone pins the desktop's certificate, on the stream and the control channel alike, and checks that the desktop holds its key.
  - A pairing code can never replace a certificate the phone already trusts for an address.
- **The phone's identity (device keys):**
  - Pairing binds the phone to the certificate it proves on the connection that pairs. The first LAN stream it then opens registers the iroh key it names there for the WAN. A WAN stream never binds a key by itself.
  - From then on, a connection that claims to be that phone with any other key, or with none, gets nothing: the stream is refused, the control channel may only pair again, and the desk is notified.
  - Each control connection is known by the id it opened with, and held to its key on every packet: pairing or unpairing (the command or the desktop app's Unpair) applies at once to connections already open.
  - Pairing again with the desktop's own PIN binds the phone's new key (a phone whose certificate changed recovers this way). `pocketdesk unpair` and the desktop app's Unpair clear the keys.
  - A guest PIN binds only an id that no phone holds. It can never take over, or extend, a paired phone's id.
- **Per-device permissions:**
  - Each paired phone can be limited to view-only, and denied the clipboard, files, sound, the microphone, power actions or commands.
  - Running commands is off until granted.
  - "Ask before each session" holds every session for that phone until someone at the desk allows it.
  - The server re-reads them each second for running sessions: a phone that is no longer paired (unpaired from the CLI or the app, an expired guest grant), or whose Input, Sound or Microphone was turned off, loses its session within a second, whatever made the change.
  - Privacy mode belongs to the phone that turned it on: no other phone can refresh or end it, and it ends once that phone is no longer paired. Turned on from another computer's screen window (PC8), it belongs to that computer the same way, and also ends as the connection or link it was asked on closes.
- **Abuse by a connection:**
  - A control packet is at most 4 MiB, on both control channels: a longer line ends the connection, before anything is buffered past that.
  - Every other packet has a size limit too, checked before it is copied or decoded (protocol.md §6): a KDE Connect device's identity line 8192 bytes, shared input's names, screen lists and sound to what its encoder makes, another computer's clipboard text 256 KiB (the owner told when one is dropped), a pairing link 8 KiB (its best 32 addresses kept), and the owner answers' lists and ids. Each of these parsers is fuzzed in CI (`fuzz/`).
  - The control and stream ports hold at most 8 connections from one address and 128 in all; more are refused. The stream port counts an address only once it has answered a QUIC Retry, so a forged source address cannot use up a phone's share. The internet (WAN) listener holds at most 128 in all.
  - One phone runs at most two file transfers at a time, within the desktop's four.
  - A device id must be printable (no control or invisible formatting characters) and at most 128 bytes, on the control channel, the stream and the v2 handshake. A device's name is held to one printable line of at most 40 characters (`clean_device_name`): cleaned where it is kept, refused in the v2 handshake when it is not already so.
  - A folder listing fits in one packet: a huge folder is listed in part, and the phone says so.
  - Refusals are logged: the first on each connection at the default level.
- **Files:**
  - Transfers run inside TLS, pinned both ways: no other device can read the bytes, send them, or take them.
  - A paired phone moves files only once its key is bound (pairing binds it).
  - Received files are confined to one folder: Downloads, or the folder the owner chose (C2, desktop Settings "Received files land in"), never Pocketdesk's own state or config folders. They never overwrite anything, are size-limited, and are marked as downloaded on Windows. A phone with Files can fill whatever folder the owner chose, as it could Downloads.
  - Browsing and downloading are confined to the home folder. Hidden files, the server's own keys and settings, network paths and device names are refused, and links that lead out of home are refused too.

## Known limits

These are real gaps in the current design. Plan around them.

1. **Without the QR code, the first contact with an address is trust on first use.** Someone who can intercept that very first connection could relay the pairing. Scanning the QR code closes this.
2. **A phone paired before device keys, that has not streamed on the LAN since, holds no key yet.** Until it does, the control channel accepts it by its id alone, and it moves no files. The first LAN stream the desktop allows binds its key, and pairing it again binds it at once.
3. **Someone who knows an unpaired phone's id can get in the way of its pairing**, by asking for PINs or spending the wrong guesses under that id. They cannot pair as it without the PIN.

4. **The Mainline DHT links the desktop's WAN id to its home IP** (roadmap N3), unless `dht_publish = "off"` or `internet_path = false`.
   - The record is public to anyone who knows the id. By default it holds the relay URLs, which name your own relay when you run one. With `"addresses"` it also holds your home's public IP addresses.
   - In every mode, the DHT nodes that store the record see the home IP it was published from, hourly, so the id can be followed to the home over time.
   - A phone's WAN dial asks the DHT for the id, which shows strangers' nodes the phone's IP and the id it is looking for.
   - The id is in the pairing QR code, on each paired phone and on every relay the desktop uses. A forged record gets nowhere: it is signed, and the phone checks the desktop's key again when it connects.
5. **The connection limits are shared.** Phones behind one public address (carrier NAT, or a forwarded port) share that address's 8 connections, so one can use up the others'. Anyone who can reach the internet listener can hold its 128 until each handshake times out; the gate still refuses them.
6. **Privacy mode is held to its phone's id, as strongly as that id is held to a key** (limit 2). If that phone's Power permission is turned off, it cannot end the grab and no other phone may, so the local keyboard and mouse stay blocked until it expires (10 minutes).
7. **The desktop names itself to anyone who connects.** Any client that completes the TLS or QUIC handshake, with any certificate, gets the desktop's device id, name and plugin list before it is judged, and its certificate. Anyone on the network sees the same id and name in the mDNS announcement unless `lan_discovery = false`.
8. **The permissions limit what a phone may ask for, not what the desktop tells it.** A paired phone with every permission off still receives the desktop's notifications, its window titles (window list and workspace HUD), its battery, the wake details (the MAC) and the internet endpoint. Unpair a phone to stop them. The clipboard is the exception: the text you copy is pushed only to phones with Clipboard on, and with "Clipboard to phones" (`clipboard_push`) off, to none, though a phone in a session can still ask for it. A copy a password manager marks private (on Windows the formats that keep it out of clipboard history, counted private too when they cannot be read; on Wayland `x-kde-passwordManagerHint`) is never pushed, nor given to a phone that asks for the clipboard (since M3); an image copied here is told of too with "Images to phones' clipboards" on (M3, off by default), to phones only, which fetch it, but other copied secrets reach every connected phone with Clipboard on. The phone's "Computer's clipboard in the background" decides only whether the text is put on its clipboard: the phone receives it while its link is up either way.

9. **A phone with Links on can open web pages in this computer's browser** (roadmap T8a), up to 5 a minute, without asking, including pages on your home network such as a router's. Only `http` and `https` links go either way, never one to the computer's own loopback (`localhost`, 127/8, `::1`, in any spelling a browser reads as one) and never one with a user name or password. Links is on for every paired phone and guest by default, as Input is, and a phone with Input can type the same link. Turn Links off per phone in the Devices tab, or set "Links from phones" (`open_links = false`) to have links shown instead of opened. On the phone, any app can share a link to "Open on computer"; it goes to the last computer used.

10. **A phone with "My media on the computer" on tells the computer what it plays** (roadmap T8d): the title, artist and app, kept owner-only in the state folder while it is connected. The computer, with that phone's Media permission on, can pause and skip it. Both sides must agree: the phone's setting (off by default) and the desktop's Media switch.

11. **With "Names from my contacts" on, the phone tells its computer who texts it** (roadmap T8e): the sender's name from the phone's contacts goes with each forwarded text and is kept owner-only in `sms.json` (turning `sms_names` off forgets the kept names at the next start). A name says what the phone's contacts call that number; a text's sender number can be spoofed, so a name is not proof of who sent it.

12. **With "Let the computer answer notifications" on, the computer can act as you in the phone's apps** (roadmap T10c): it can press a notification's buttons (up to three, by title, never one Android runs only once the phone is unlocked) and reply to a chat, from the desktop app's Notifications page or, since N3, from the notification itself (a Windows toast's buttons and reply box; a Linux notification's actions and KDE's inline reply), at most 10 a minute. A toast can pop up under the cursor while you work, so one stray click presses whatever the phone's app offered ("Delete", "Archive"); desktop Settings "Answer in the notification" (`toast_answers`) turns that path off and leaves the Notifications page. Only a notification sent in full (not one whose content the lock screen hides, nor one carrying a code), and only from the phone's own computer. The notifications that can be answered are kept owner-only in `phone_notifications.json` while the server runs. It is off by default, and the desktop's Notifications switch for the phone turns it off too.

13. **The folders a phone shares (roadmap T10g) can be read by its computer.** In the desktop app's Phone tab, or by anything running as you that writes its requests, the computer lists them and copies any file in them, hidden ones (a leading dot) left out. Only folders the phone's owner picked in Settings, "Folders the computer may open", and only from that phone's own computer, with its Files permission on. Removing a folder there gives its grant back.

14. **With "New screenshots to the computer" on (roadmap T10h), every screenshot taken on the phone goes to its computer**, whatever it shows: onto the computer's clipboard and into its Downloads. On the computer it is then in the clipboard's history (Windows' Win+V, and its cloud clipboard if that is on) and in Downloads. Only to the phone's own computer, only images in a folder named `Screenshots` (an app that drops other images there sends them too), at most 10 minutes old; the computer's Clipboard and Files permissions gate each half. It is off by default.

15. **A phone's cast shows everything on its screen on the computer** (roadmap T10k), notifications and codes included, to whoever sees the computer's screen, while the phone's owner casts it. Android asks for consent each time, and its status bar shows that the screen is shared. The computer hands the picture from the server to the desktop app over loopback TCP, behind a token only its owner can read (`cast.json`); any program running as that owner can read the token, and so watch the cast. The Cast permission ("Show its screen or camera here", on by default) refuses it per phone; the same permission covers the phone's camera shown in that window (F6), which shows whatever the camera sees.

16. **The event log and hooks keep a record of what happens, and run what you tell them** (ecosystem phase 1a). `events.jsonl` in the state folder (owner-only, 1 MiB and one older file kept) lists sessions, phones linking, batteries, and the notifications, texts, files and links that arrive. By default it records only who, when and how much: the app a notification came from, a file's size, a link's host. With "details in events" on (`events_detail = "full"`) it also keeps their content (notification and text bodies, senders, file names, whole links), on disk, until the log rotates. A hook in `[hooks]` runs as you, with the event on stdin and in `POCKETDESK_EVENT`, through the shell: treat the event's fields as untrusted text (a phone chooses a notification's text and a file's name), and read the event from stdin: on Windows `%POCKETDESK_EVENT%` in a hook's command line is expanded before cmd parses it, so a phone-chosen field could run commands. A hook is stopped after 30 s, but programs it started in the background may go on. Turning "Event log" off writes nothing; hooks still run.

17. **A phone with the Tasks permission can run the commands you named as tasks** (ecosystem phase 1c), as you, through the shell: only those, by name, never a command of its choosing (that is Exec, off by default). "Ask first" is on for a new task, and holds each start for your Allow in the desktop app (a minute, then denied); turn it off only for a task that is harmless whenever it runs. Tasks is on by default for every paired phone and guest grant, like the other permissions but Exec, but nothing runs until you name a task. A run stops at its time limit (60 s unless you set another, at most an hour), though programs it starts in the background may go on. A phone may ask for 10 starts a minute, and a start that asks first holds one of the 2 places while it waits for you (up to a minute), so a paired phone can keep your other tasks waiting and keep asking.

18. **The browser extension can make this computer send a page, a link or an image to your phone** (ecosystem phase 1d), when you right-click one: the browser starts `pocketdesk browser-host` as you, and only the Pocketdesk extension's id may talk to it. For an image, Pocketdesk downloads the address itself (`http`/`https`, never the computer's own `localhost`, the address and each of at most 5 redirects alike, though a name that resolves to an address on your network is not refused; at most 32 MB, only a PNG, JPEG, GIF, WebP, AVIF or BMP by its content type, and named for that type: an address ending `.apk` arrives as a `.png`; SVG is not sent), so the site sees this computer fetch it, not the browser. The phone's Links and Files permissions apply. Another extension cannot reach the host, but anything running as you could run it, as it could any of your programs.

19. **Home Assistant sees your computer and phones, and can start your tasks** (ecosystem phase 1e), when you turn it on and name an MQTT broker. The server publishes, retained: whether it runs, the number of sessions, whether a phone's screen is shown, each paired phone's battery and connection, and your tasks' names (never their commands). Not retained, as they happen: each event's kind and phone, so the broker learns that a notification, a text, a file or a link arrived and from which phone (by the first 8 characters of its id), never what it said or was called. The connection is plain MQTT, so anyone on the network path can read it and the password, and anyone the broker lets publish to `pocketdesk/<computer>/task/…/run` can press a task's button: a task that asks first still waits for your Allow at the desk, but one that does not ask runs. Give the broker a password, keep it on your own network, and leave "ask first" on for any task you would not let your broker start. The password sits in config.toml, which Pocketdesk writes readable only by you; a config.toml you wrote by hand keeps the permissions you gave it until Settings saves it. Turning the bridge off marks the entities unavailable in Home Assistant; delete the device there to remove them.

20. **With "Tell other apps what happens" on, any app on the phone learns when you use Pocketdesk** (ecosystem phase 1f): the broadcasts name no app, since an automation app cannot hold a permission of ours, so any app may hear when a session starts and ends, a file or link arrives, files finish sending or a task ends, with the computer's saved address, a file's type and size, and a task's name and exit code. Never a file's name, a link, a task's output or a notification. Any app can also send the same broadcasts, so an automation should not treat one as proof that it happened. Off by default.

21. **Another of your computers, once paired, may do what a phone with Clipboard, Files and Links may** (ecosystem 2f, 2g): browse and fetch files under your home folder, send links that open in your browser, and, with "Clipboard with my computers" on on both, share the clipboard both ways (text, and with no text an image, which rides the link's file streams and so only with "Files over the internet" on; a password manager's private copies stay where they are). It may not send input, sound, power or commands, except: input with Keyboard and mouse on for it (limit 59), with "Control the mouse and keyboard" for its screen window (limit 62), or paired both ways (limit 64); sound both ways, hearing this computer while its pointer is here (limit 61) and sending its microphone from its screen window (limit 70, on by default only for a computer paired both ways); privacy mode and the lock, with "Lock, sleep, privacy and wake others" on for it (limit 69); and waking this computer, paired both ways, which tells it this computer's MAC (limit 68). A screen session from it (limit 62) is held for you to allow, unless the two computers are paired both ways (limit 64), when nothing is held. Pairing it takes your PIN, inside the pairing link that the Pair tab copies, so treat that link as the PIN: Pocketdesk never sends a pairing link from the clipboard to a phone or a computer, but it stays on this computer's clipboard (and in Windows' clipboard history) until you copy something else; its certificate is pinned from the link before the PIN is sent. Unpairing on one computer does not unpair it on the other: unpair it in the other's Devices page too. The link between them rides the internet path (iroh), so relays and the DHT see what they see for a phone (the start of this page, and limit 4). A computer running a Pocketdesk from before this pairs the other as a phone, with a phone's default permissions: update both first.

22. **KDE Connect devices can find this computer and connect to it, on by default** (ecosystem 3a; desktop Settings "KDE Connect devices" turns it off). The desktop app's "Find KDE Connect devices" broadcasts this computer's name and a KDE id of its own on the local network; a device that hears it (or knows the address) dials the control port. That path takes TLS 1.2 as well as 1.3, since KDE Connect Android caps at 1.2, and holds a device to the id its certificate names; the Pocketdesk road stays TLS 1.3 only. A device that has not paired is given nothing (at most 4 such links from one address, closed after 5 silent minutes, one pairing request at a time each). Pairing (3b) is held for you with a code both screens show, either way: a device's request waits for your Allow, and a device's acceptance of yours waits for your Confirm. **The code is the only check**: any device on the network can ask, under any name, and can claim a device's id while that device is not connected, so compare the code on both screens before you answer, and do not answer a request you did not expect. Your answer names the code you saw, so it is not taken for a request made since. Once paired, a device reconnects only with the certificate it paired with, and may do only what its own switches allow (3c), narrower than a phone's: ping; its battery; the clipboard both ways (your copies go to it while "Clipboard to phones" is on); being rung from here; and, only when you turn it on, sending files into Downloads (fetched from the device's own address, held to its paired certificate, marked as downloaded); and its notifications (N9, on by default, sent only with notification sync on in its own KDE Connect app), **shown here in full**: unlike Pocketdesk's phone app, which keeps lock-screen-private content and one-time codes off the computer, KDE Connect sends what it sends and this computer cannot tell what is private, so the text reaches the toast, the notification centre and, with "details in events", the event log and hooks; turn the device's "Show its notifications here" off, or choose apps in its KDE Connect app. Nothing else it sends is taken, Pocketdesk's own packets among them. A file stops on the way if you unpair the device or turn Files off, and a device sends at most 4 at once.

23. **Your computer can ring a paired phone loudly** (N1): its Ring button or `pocketdesk ring` make the phone ring for 30 s at its alarm stream's full volume (at the owner's alarm volume on Android 17 and newer, where an app may not raise it from the background), through Do Not Disturb when alarms may sound. Only a paired phone with its Ring permission on (Devices) and its own "Ring from the computer" on, or a session or the remote open, rings; at most once a minute, and never another computer. Anyone who can use the owner's account on the computer can therefore ring the phone.
24. **With "Remember the screen-sharing grant" on, sessions start with no one at the computer** (N8; GNOME and KDE, off by default): the portal's grant to share the screen (and, where input goes through the portal, to drive the keyboard and pointer) is kept until revoked, with its restore token owner-only in the state folder (`portal_restore_token`, `portal_remote_token`). Anyone who can read your state folder can start a screen share as you, without asking; every session is still held to a paired phone, its key and its permissions, and "ask first" where set. Revoke it in the desktop's own privacy settings (GNOME: Privacy, Screen Sharing; KDE: the portal's permissions). Forget the grant in the app, or turning the setting off, only drops the local token, so the next session asks again; the desktop's own permission stays until revoked there. KDE Plasma can also be told to allow Pocketdesk ahead (the guide's "KDE Plasma: No Dialog at All"): that is a standing grant of the screen, keyboard and pointer to whatever program names itself `dev.pocketdesk.Pocketdesk` to the portal, and the portal does not check that name, so **any program running as you can then share your screen and drive it without asking**. It is off unless you set it; prefer "Remember the screen-sharing grant" unless no one is ever at the computer, and take it back with `flatpak permission-remove kde-authorized remote-desktop dev.pocketdesk.Pocketdesk`.
25. **With the phone's "Let the computer control this phone" on, the computer it shows its screen to can act on it** (C8; off by default, and it needs an Accessibility service the owner turns on in Android's settings).
    - **What it can do:** only during a cast, and only from the computer the phone itself opened the cast to, that computer can tap, drag, scroll, type into the focused field, and press Back, Home, Recents and the shade. Nothing is touched or typed while the phone is locked, so the computer cannot enter its PIN or pattern; Back and Home still go.
    - **On the computer:** any process running as the owner that can read the cast's token (`cast.json`, owner-only) can send control. The desktop app's "Control phones from their screen window" is the app's own choice, not a gate the server enforces. The phone's setting is the real gate.
    - **What Android allows:** the service may read the screen. Pocketdesk reads only the field it types into and sends nothing it reads.
    - **Advanced Protection:** Android 17's Advanced Protection does not allow the service.

26. **With the phone's "Recent photos on the computer" on, its computer can see its newest camera photos** (C7; off by default, and it needs photo access). The computer asks; the phone answers its own computer only, with thumbnails of at most 24 photos in DCIM, and sends a full photo only when asked, through the usual transfer. The thumbnails are kept owner-only in the computer's state folder, so anyone who can read that folder, or use the owner's account on the computer, can see them; turning the switch off on the phone stops further answers, and they are dropped when the server starts again.
27. **With the phone's "Let the computer mute this phone" on, its computer can turn on its Do Not Disturb** (D2; off by default). The computer asks with a number of minutes, at most a day; the phone takes it only from its own computer, only when it is not already quiet, and ends it at its time unless the owner changed it meanwhile. Meanwhile calls and messages the owner's own Do Not Disturb settings let through still come, but others are silenced: anyone who can use the owner's account on the computer, with the phone's Mute permission on (Devices), can quiet the phone for up to a day at a time. The phone also tells that computer whether it is in Do Not Disturb, which says something about the owner's day.
28. **With "Clipboard history" above 0, the computer keeps in plain text what crossed** (D3; off by default). The last texts that went between this computer and its phones, either way, sit in `clip_history.json` in the state folder, owner-only, until they fall off the end, the history is cleared, or it is turned off. A copy a password manager marks private never crosses and so is never there, but a secret copied without that mark, or one the phone's tile sent after you confirmed it, is; so is a KDE Connect device's text. Anyone who can read your state folder, or use your account on the computer, can read them. A pairing link, anywhere in a copy, is never kept.
29. **With "Let the computer answer notifications" on, a chat's recent messages reach the computer** (D4). For a chat notification sent in full, its newest ten messages, other people's names and texts included, go to the computer, where they are kept owner-only with the notification (`phone_notifications.json`, the newest 30). A thread in which any message looks like a one-time code is not sent. Anyone who can read your state folder, or use your account on the computer, can read them; turn answering off in the phone's Settings to keep them on the phone.
30. **With "The phone's folders as a drive" on, any program on the computer that has the drive's address can read the folders the phones share** (D8; off by default). The server serves them read-only as WebDAV on loopback only, at an address with a random token in it, kept owner-only in `drive.json` and new each time the drive starts. Anyone who can read your state folder, or run programs as you, can find the address and read every folder a phone shares while it is connected, as the Phone page can. Files fetched through it wait in `drive_cache/`, owner-only, until served.
31. **"Lock this computer when it leaves" is a convenience, not a boundary** (D9; off by default; Windows, and Linux under GNOME, KDE on X11 or X11, R3). The computer locks when the phone's link has been gone for a while and nobody has used the keyboard or mouse, so a phone that keeps its link from across the house, or that someone else keeps near the computer, keeps it unlocked; and a link can drop for other reasons (the phone asleep, Wi-Fi), so it may lock while you read. A lock that fails is tried again a minute later. Lock the computer yourself when it matters.
32. **A deck button does its action as the phone pressing it may** (F1). The buttons are yours, set up in the desktop app's Settings, and a phone sees only their labels; but a phone with "Control the mouse and keyboard" can press a button's keys or type its text on the computer without a session, as its mouse and keyboard packets already can, a task button starts the task as a phone's start does (asking first when the task asks), and a link button opens its link. Leave out of the deck what a phone should not set off; turn "Deck" off in Settings to refuse every press.
33. **A paired phone may see how this computer is doing** (F2; on by default): the CPU and memory in use, each fixed disk by its drive letter or mount point (a Linux mount point can hold your user name), the battery and uptime. Turn "This computer's state" off in desktop Settings to answer none of it.
34. **With "Ringing calls on the computer" on, the caller reaches the computer** (F5; off by default): the number, and the contact's name with "Names from my contacts", as the phone's own notification, whatever the phone's lock-screen privacy or its notifications switch say; and the computer may then silence the ring or, with "Let the computer decline calls", end the call.

While a link is on, Windows' own Settings shows and lets you change the hotspot; turning it off there ends the network but not the code on the Pair page, which stays until the idle time or the eight hours end the link. **What it does not do:** it does not hide the network (it is visible to every phone nearby while on), it does not limit how many devices join (anyone with the passphrase can), and it does not make Pocketdesk's own control channel any more private than at home (the PIN still travels the control channel; scan the code, which pins the certificate first).

79. **Hands-free apps: a paused screen share, a screen-sharing question accepted by the phone, and a lock screen swiped away** (building on limit 78). **Nothing here is on until the phone's owner turns on "Let the computer open my apps"**; the one new switch is "Accept screen sharing for my computers" (phone Settings, **off by default**), and none of it needs a new Android permission, adb, Shizuku or wireless debugging. It holds only for the phone's own computer, never a guest's or another's. **A paused share** needs both switches on. When the computer leaves a screen it was showing (and the link did not end for a refusal, a changed permission or an unpairing), the phone keeps the consent already given for at most ten minutes, with the projection and its virtual display kept and **nothing captured** (no encoder, no surface), its ongoing notification up with Stop the whole time, and the same computer's next open resumes it. It never resumes for another computer (a new consent drops the old one first). It ends at Stop, at Android's own stop of the projection, at ten minutes, and **within two seconds of either switch being turned off or the computer no longer being the phone's own paired computer** (a watch every two seconds while paused, not only a check when it is next asked for). Whether Android also stops a projection when the phone locks depends on the Android version and maker and is not relied on here (it is an owed device check): where it does not, a paused share runs on, capturing nothing, until one of the ends above. The cost is that for those ten minutes the owner's earlier consent can be used again by that computer without a new question; it cannot show anything it was not already allowed to show, and the notification and Android's own indicator stay. **An accepted question:** with the opt-in on, when an open from the phone's own computer needs a screen share, Pocketdesk launches Android's screen-capture question itself and the control service presses its confirm button. It is bounded so that it can press nothing else. It is armed only by Pocketdesk's own window, as it launches the question for an ask the own computer made (the opt-in, the apps switch, the own computer and the bound service are checked again at that moment). **The question is identified exactly:** Pocketdesk takes the package and class of the activity named by the very intent it launches (an explicit component, else the resolver's answer; none known means nothing is pressed); the service listens, only while armed, for the window-state event of exactly that package and class, keeps that event's window id, and reads and presses only that one window, never "any window of SystemUI". That window's text must name Pocketdesk by its exact label (as `loadLabel` gives it) as a whole word or phrase, not inside a longer word. It looks for five seconds after the launch for the window and eight after it is seen, and ends at its first press; with no ask waiting it never acts. It presses only that window's confirm button by the node's own click action, found by its id or class, never by a coordinate, **and only when the button's words are one of a list of known confirm words ("Start now", "Share screen" and their translations in the languages Android ships most); any other words, an unknown language, "Next" or "Cancel", are never pressed.** It never opens a chooser and never picks a row: on Android 14 and later the question is raised for the entire screen of the default display only, so it has no one-app choice; if a chooser is nonetheless on the window (an OEM layout), the button is pressed only when the chooser itself reads "entire screen", and when it reads one app, reads nothing or reads a language not known, nothing is pressed. Where no chooser is recognised, the button is pressed only by the rule above (known confirm words). What it sees is compared and dropped: only the outcome ("pressed", "not found") and a count of looks are logged, never the screen's words. If the window is not found, its button is hidden from accessibility (Android may mark a window so), or an OEM lays it out differently, nothing is pressed, the one-tap notification is offered as before, and the computer is told `needs_tap`. **The cost of the opt-in:** the Accessibility service already can press a button in any window the owner turned it on for; this adds nothing it could not do, but it uses that to answer, for the owner, a question Android meant the owner to answer, so it is off until the owner chooses it, and the screen it then shares goes only to the phone's own computer, as limit 78. **A locked phone:** a lock screen with no secret behind it (swipe only), or one Android has already unlocked (Extend Unlock, Smart Lock or a biometric that has accepted, so `isDeviceLocked` is false), is dismissed by Android's own `requestDismissKeyguard` from a transparent window the control service starts, and a screen that is off is woken, for an open only. The window is started by nothing but that ask, looks at the lock again at the moment it acts (it shows over the lock and turns the screen on only from code after that look, never by a manifest flag) and does nothing under a secure one; after a wake or a dismissal it reads Android's answers again and counts only a phone that is awake with no lock screen over it as open (never Android's callback alone); a dismissal that is not answered within 2.5 seconds (Android is asking for a secret) is given up on; and the lock is read once more right before the app is started or the screen share asked for. **A secure lock (PIN, pattern, password or a biometric lock that is on) is never bypassed:** the phone answers `locked_secure`, and the computer says to unlock the phone or to let Android keep it unlocked near this computer (Settings, Security, Extend Unlock / Smart Lock, Trusted devices; the name varies), which is Android's own policy and the owner's choice. **What it does not cover:** the lock-screen dismissal and the accepted question are as strong as the apps switch (any program running as you on the computer can queue an open through `phone_actions_out/`, limit 78), so a phone with no secret on its lock screen and the opt-in on can be made to share its screen by any such program; a phone with a secure lock cannot.
80. **A phone can keep folders on this computer, and its files then land, replace and (with two switches) vanish there by themselves** (the phone's "Folders kept on my computer", the computer's `kept_folders`, **on by default**, owner phones only). Each folder is the owner's own pick on the phone, with Android's folder picker (read access to that folder alone, no storage-wide permission), and the phone copies it one way to the computer it names, on a schedule (on Wi-Fi while charging by default, or every few hours on Wi-Fi). **What it opens:** an owner phone, with no one at this computer, writes files below `Documents/Pocketdesk phones/<phone>/<folder>/` (or `kept_folders_root`), each replacing the file of the same name, until the folders hold `kept_folders_cap_gb` (50 GB by default, 0 for none); and, only when the phone's "Mirror deletions" (off by default) **and** this computer's `kept_folders_allow_delete` (off by default) are both on, deletes plain files below that phone's own folder. **What bounds it:** the packets are a share with a `keep` mark and a run's end (`kdeconnect.pocketdesk.keep_run`), both held to the Files permission and to an owner phone (`TrustStore::is_owner_phone`: never a guest's, someone else's, a time-limited one or a computer), with `kept_folders` on; a list of folders this version cannot read is never written over (a copy is kept beside it, and every run is refused until it is fixed), so no record is dropped; the registry holds at most 64 phone folders; a deletion names a path that is checked again here, removes only a plain file (never a folder or a link) below that phone's folder, and the folders it leaves empty up to the kept folder, and the phone sends none when it could read only part of the folder (a listing that failed, a row the provider gave half, a walk cut short), when its listing holds no file while it kept some, or when more than half of what it kept is gone at once (two or more), so a card taken out cannot empty the copy; this computer holds the same line itself, whatever the phone says: it refuses a run's deletions that, with what that run deleted before, are over half of the files the folder held at the run's last count (unless two or fewer) or over 1000 in all, and counts and says so on the Files page, logging counts and no names; a delete by one spelling of a name never removes another that differs only by case, and a name spelled otherwise than the file on the disk deletes nothing; files get the Mark of the Web on Windows. **What it does not cover:** a phone of yours that is lost or taken over (not yet unpaired) can fill the cap with files of its own and replace files in its own kept folders, and, if you turned both deletion switches on, delete any plain file below its own kept folder here (this computer does not remember which files the phone sent, only the folder's place), so keep nothing there you would miss, and leave the computer's deletion switch off unless you want mirrored deletions. The files here are your phone's, readable by any program of this user, as Downloads is. Hidden files and folders on the phone are not kept. A computer too old to know kept folders is detected by the phone before it sends (it says so, and sends nothing), because such a computer would take the files as a folder send into Downloads.

82. **A spare phone at home can wake your computer for your other phones, from anywhere** (Wake helper for this home on the phone, **off by default**; Wake through my helper on each of your other phones, per computer, **off by default**). **What it opens:** the helper phone runs an iroh endpoint (on its own key, `pocketdesk-wake/1` only) while the switch is on, the phone is on a charger and on Wi-Fi, and the phone's own Android foreground service says so in its notification; the endpoint is closed the moment either goes. The phone serves one thing, "send the magic packet for this computer", and nothing else (no file, no control, no packet type of the control channel is reachable on that ALPN). **Who may ask:** only an iroh key the computer put in the helper's duty, which is each owner phone of that computer that registered one (a phone paired with the computer's own code, never a guest's, someone else's, a time-limited one or a computer), for that computer only; any other key is closed before a byte is read, a key introduced for another computer is told `unknown`. The helper phone itself is a phone of yours that offered itself to the computer; the computer takes the offer only from an owner phone, keeps one helper, and notifies you when it changes. **What is sent:** the magic packet is built from the MAC the **computer** told the helper (found by the computer from the adapter whose subnet holds the helper's own address, never from anything the helper or the asker said; the request carries only the computer's id and a line with any other field is refused unread) and goes to `255.255.255.255` and to that network's broadcast address only when it is one of the networks the helper is on now, so a computer cannot make the helper send a packet anywhere else. The helper also sends nothing at all unless that broadcast address is one of its own networks now: a helper taken to another Wi-Fi never broadcasts your home computer's MAC there. A handshake that is not finished in 2 seconds is dropped (4 connections at once), and a relay a phone is told to use must be `https`. It wakes a computer; it does not log in, unlock or give anything else. **What bounds it:** a burst of 2 and then one every 30 seconds per asking key, 6 and then one every 10 seconds in all, 4 connections at once, a 512-byte line within 5 seconds; the helper phone keeps a duty only from its own computer, only while its switch is on, only when the computer's id is the one it paired that address with; the owner can remove the helper on the computer (desktop Settings, Wake), and the phone's switch then goes off and stays off until its owner turns it on again (a removal is remembered, so a phone that keeps offering is refused). **Removing is not a security control:** whoever holds that phone can switch it on again, and the computer will take it as helper again; to take a phone's access away, unpair it; the log says only that a wake was served, dropped or refused, never a key, a MAC or an address (counts and outcomes only). **No new Android permission:** the service is `connectedDevice`, as the link service is, and reads only the battery and the network. **What it does not cover:** (a) The helper's copy of the owner phones' keys is as fresh as the last time the computer, awake and linked, told it (checked every 15 seconds and told again every hour while linked): **a phone of yours that is lost can still ask the helper for a wake until the helper hears the computer again.** While the helper is linked to the awake computer that is **under a minute** after you remove the phone; **a helper that is switched off, out of reach, off the home network or whose computer is asleep keeps its last list until it hears the computer again, and drops a list it has not heard in a week** (a computer that revokes the phone while asleep cannot; it tells the helper when it is next awake and linked). A computer that cannot work out a helper's duty (the helper is on none of its networks, or only a tunnel) tells it so and the helper drops what it held for that computer. A lost phone of yours can wake your computer, and nothing more, as a lost phone could with its own Wake button; remove it from the computer's Devices page at once. (b) The helper phone holds your computer's MAC and your owner phones' iroh keys, which are public keys, not secrets; a stolen helper phone gives no one a key to ask with, but tells them your computer's hardware address and which keys you use; unpair or turn off the helper, and remove it in Settings, when it is lost. (c) The relays n0 runs (or yours, once the computer announces its own) see the helper's and the asking phone's public addresses and ids, and when they talk, never what is said, as for any internet connection (limit 4). (d) The phone must reach the helper through a relay: its relay address is told by the helper while it listens, and a helper whose relay changed while the computer slept is reached only after it offers again (every 10 minutes while linked; waking is then tried through the relay it last named). (e) The helper phone serves the computer it is linked with (its own computer); a second computer does not get a helper from the same phone until it is linked there. (f) Keeping a phone on a charger with a service in the foreground is the owner's own choice, with the battery cost Android gives any foreground service.
83. **Phone apps can run on a screen of their own through Shizuku, which gives Pocketdesk's helper process shell identity** (Phone apps tier 2, "Separate windows (Shizuku)", **off by default**, Android 10 or later, and shown only while Shizuku is installed and running). It adds no Android permission to Pocketdesk and nobody is told to install or start Shizuku or to turn on wireless debugging; a phone that does not run Shizuku is unchanged, and so is one that does until its owner turns the switch on, which brings Shizuku's own permission dialog once (that grant is the owner's, and Shizuku's manager takes it back). **What shell identity is:** Shizuku starts a helper process of Pocketdesk's as uid 2000, which can do much that an app cannot. Pocketdesk uses it for exactly three things for windows (and, separately, two calls that take no argument and turn the phone's own hotspot on and off, which are limit 85), through one small interface (`IWindowHost`): make a display of its own for an app window and give it back, start an app on that display (`am start --display <id> -n <package>/<class>`, the component read from the launcher by the phone itself and held to a package, a slash and a class name before the shell sees it), and send touch, wheel, Back and typed text to that display (events are given the display's id before they are injected, and an event is injected only if that call exists, so none lands on the phone's own screen; in a session of windows alone every control batch that is not for a window is dropped by the phone, as the phone's own screen is then not being shown; only Back, Enter and Delete are pressed, and touch, wheel and text, never Home, Power or Recents). It reads no screen, file, message or setting, runs no command but `am start` with the arguments above, takes calls only from Pocketdesk's own uid (and Shizuku's own server, to end it), and exits when the last window closes, the switch goes off or the cast ends. At most four windows at once, 10 asks a minute as for any open. A window's size is held to 240 to 3840 pixels and a density to 120 to 640. **What the computer then sees and does:** each window is its own video stream of the phone's existing connection to that computer (the phone's own screen is not captured, and no screen-capture consent is involved), shown only in a window of that computer's own app, over the loopback connection the phone's screen window already uses, with its own token; the computer's touch, scroll and typing there reach that one app (a viewer of one window cannot name another), and only while the phone said that window takes them (its switch is the same one); anything typed or tapped reaches the app as if on the phone, so a window of a banking or messaging app shows and takes what that app does, to whoever sees that computer's screen. For aiming the desktop window can lock and hide this computer's pointer (the same lock as viewing another computer, off until the owner asks, freed by Ctrl+Alt+Shift+M, by Ctrl+Alt+Shift pressed and let go alone, by losing the focus and by closing, with a note over the picture for as long as it is locked); while it is locked the window takes the mouse's movement and buttons as the keymap's and nothing else (where the system cannot lock the pointer, as on Windows and X11, it is confined to the window and kept in the middle instead). The cost is the same as for typing in a window: whoever can use that computer's window can play or tap whatever the app does, and a game that watches for injected input may flag the account, which Pocketdesk cannot see (the computer says so beside the switch and the guide says so). **What it is not:** Pocketdesk does not store or pass on Shizuku's grant, never asks for adb, and uses no hidden API outside the helper process. The display and input calls are written for this app on the technique scrcpy (Apache-2.0) uses; none of its code, and none of RustDesk's or Sunshine's, is copied. 84. **Watch controls: a Wear OS watch pressing the phone's own buttons over Bluetooth** (item 9 of next-plan-3). **Off until the owner turns on "Watch controls" on the phone**, and each of its five buttons (Wake, Ring this phone, the computer's music, Deck buttons, Questions) has its own switch; Deck is off until chosen. Turning it on asks for Android's nearby-devices permission once (Android 12 and later; Bluetooth permissions before that are install-time); no scan, no location, no Google Play services, no Data Layer, and nothing new opens on the computer. While the setting is on, the phone's notification-listener process listens on one secure Bluetooth (RFCOMM) service, so only a device already bonded with the phone can open it, and a connection is let in only from the watch's own Bluetooth address saved at pairing (apart from the two-minute pairing window below). **Each request is authenticated:** the phone sends a fresh random challenge on connecting, and every request carries its op, a counter and an HMAC-SHA256 under a 32-byte key the phone made at pairing, over the challenge, the op, the counter and the body, so another program on a bonded device (earbuds, a car) cannot make a valid one, a request recorded in one connection does not fit the next, and a replay in the same connection does not beat the counter; the answer carries a MAC too, so a service that is not the phone is not believed. A frame that does not verify gets no answer, and three in a row end the connection; a frame is never trusted for its size (2048 bytes at most). The phone limits repeats for the whole phone (a ring once a minute, a wake every 10 s, a deck press every 1.5 s), so a watch that reconnects does not start over. **Pairing** is six digits the watch shows and the owner types on the phone with the pairing screen open; the watch proves it knows them with a MAC over the phone's challenge, its name and a fresh ephemeral key, and the phone sends the 32-byte key masked by a pad made from the digits and an ECDH (P-256) secret from that key. **Six digits are only about 20 bits:** what protects the exchange is the Bluetooth bond's encryption (only a device already bonded can connect at all), and the ECDH secret means that even someone who recorded the exchange and guessed the digits does not get the key. The two devices' Bluetooth addresses are not bound in, because Android hides an app's own device address, so the two sides cannot both name both (they cross the air in the clear anyway). A wrong code counts against the Bluetooth address that sent it: three per address and ten in all close the window, so a rogue bonded device cannot use up the owner's tries; one connection per address waits at a time, and the window lasts two minutes at most. **What a button is:** the same code the phone's own tiles and widgets run, so the computer sees the phone and only what the computer already lets the phone do (the phone's wake settings, the phone's Audio and Deck permissions); a watch never reaches the computer another way. **A watch cannot say Yes:** the wire has no op that answers Yes. "Approve with my phone" signs with a phone Keystore key that needs the phone's own fingerprint or screen lock for each use (limit 73), and a plain question's Yes takes the phone's lock; a watch's lock cannot stand in for either, so those stay on the phone, and the watch can only list the question and say No (which only stops something, as on the phone). The words of an approval request on the watch are made on the phone from its fields (never the free text); a plain question's text comes from the computer and is cleaned of control and direction characters and cut to 120 characters. A deck button and a No take the watch's own lock (a lock set and unlocked), **checked on the watch only**: the phone cannot see the watch's lock, so a modified watch app, or anything holding the key, skips it. **What it does not cover, the cost:** the key lives in each app's private storage on the phone and on the watch (left out of backups and transfers, not wrapped by the Keystore), so someone who can read either app's data, or who holds a paired, unlocked watch, can wake the computer, ring the phone (30 s, Stop on the phone), control the computer's music and say No to its questions, and with Deck on press the deck's buttons; that is no more than the phone's own lock screen widgets allow, and no Yes. A device bonded with the phone but not paired gets nothing: with the pairing window closed its connection is closed at once, with no challenge sent, and with it open it can only try the code (three tries per address). Stopping the service or forgetting the watch closes every open connection. Turn "Watch controls" off to stop the service; "Forget" on the phone deletes the key.

85. **Your own computer can ask your phone to turn on its Wi-Fi hotspot, through the same Shizuku helper as limit 83** (Let my computers turn on my hotspot, on the phone, **off by default**, Android 11 or later, and shown only while Shizuku is installed and running; "Use my phone's hotspot" on the computer's Overview, shown only for a phone that says its own switch is on). It adds no Android permission, asks for no adb or wireless debugging, and a phone that does not run Shizuku is unchanged. **What the helper does for it:** two calls, `startHotspot` and `stopHotspot`, appended to the helper's interface (transactions 9 and 10; none renumbered), and **neither takes any argument**: no network name, password, band or any other value is ever passed in, from the computer or from the app. Starting asks Android's own tethering manager, the service the phone's Settings hotspot switch uses, to start Wi-Fi tethering with no provisioning screen, so the hotspot starts exactly as its owner already set it in Android (name, password, band, security). Stopping asks the same manager, and if it does not answer runs one fixed command with no shell and nothing from any caller: `/system/bin/cmd wifi stop-softap`. (`cmd wifi start-softap` is not used: it needs a name and a password on its command line, which this app never passes.) The calls go through the same caller check as every call in limit 83 (only this app's own uid, and Shizuku's server to end the helper). **What travels:** the computer sends `{action: "hotspot_on"}` or `{action: "hotspot_off"}` and nothing else (an ask with any other word is dropped), and the phone sends nothing back about the network: the computer never learns the phone's hotspot name or password from Pocketdesk. **Who can ask:** only the phone's own computer (never a guest's, another's or a time-limited one), with the switch on (an ask to turn it **off** is also taken with the switch off, so the owner is never left with a hotspot the computer cannot end), Shizuku running and allowed, and at most 8 asks in 10 minutes. **A locked phone may still turn it on, by choice:** a hotspot shows no screen content and opens no app, Android shows its own hotspot indicator, and a computer wanting internet is most often away from a phone in a pocket; so no lock or screen state is asked, only the rules above. **Turning it off:** Pocketdesk keeps a record of a hotspot it turned on (when that run began, when it was last asked for, and which computer asked) until a stop has gone through, and turns it off: when the computer asks ("Turn its hotspot off"); after the minutes set on the phone (15, 30, 60 or 120, default 30, or never), counted from the last ask to turn it on and checked at the phone's ordinary tick, so it is a timer renewed by each ask, not a measure of whether the computer is using it; **after 4 hours from the first ask of that run, whatever the setting says (including never), and a later ask never moves that cap**; when the asking computer's link has been gone for 2 minutes; at once when that computer is unpaired, revoked or removed from the phone; and when the owner turns the switch off. A stop that does not go through (Shizuku stopped, the call failed, the helper did not answer within 45 seconds) is never forgotten: it is tried again every 15 seconds, and so when Shizuku is back, until it has. **A hotspot the owner turned on themselves is never recorded, so none of these turns it off:** before starting, the helper asks the tethering manager whether a Wi-Fi hotspot is already running and, if one is, starts nothing and records nothing (a USB or Bluetooth tether does not count; if the manager cannot be asked, it starts as before and the hotspot is recorded as ours). The one thing that ends the owner's own hotspot is an explicit "Turn its hotspot off" from the computer. **What it costs:** while the hotspot is on, anyone in range who has its password can join and use the phone's mobile data, as if the owner had turned it on, and a device that joins is on a network with the phone itself, so it can reach whatever the phone offers on that network, not only the internet; and it drains the battery; your carrier's terms on tethering are yours to read. Keep a strong hotspot password in Android, leave the auto-off on, and leave the switch off on a phone you do not fully trust the computer with. **The computer's side:** by default it only tells you to connect. On Linux with NetworkManager, you may type your phone's hotspot name in Settings (`phone_hotspot_network`, empty by default) and it then runs `nmcli connection up uuid <uuid>`, no shell, only if that name is exactly one saved Wi-Fi connection on this computer (listed first with `nmcli -t -f NAME,UUID,TYPE connection show`; with two of that name, or none, nothing is joined, and the connection is named by its UUID so no other can be brought up); the name is held to 32 bytes, no control character and no leading dash, and `device wifi connect` (which takes a password) is never used, so Pocketdesk never asks for, reads, stores or sends the hotspot's password. **Not yet checked on a real phone:** the tethering-manager call is reflection on hidden Android APIs, which a shell process may use, written from the platform's source and not run on a device yet; it answers "it did not start" rather than throwing, and the device checklist (section 266) lists the phones it is owed on.

86. **Another of your computers can take one of this computer's windows off its screen and show it on its own** (window lending, phase 3a of the window handoff, **off by default**: Settings, Other computers, "Let my computers borrow my windows", `lend_windows`; Sway and Hyprland 0.56 on; Windows is limit 88; no other desktop). **What it adds:** a computer paired both ways ("both are mine", its grant neither pending nor lapsed) that has the Input permission here can ask, by a window's id, for that window to be moved to a hidden headless screen of its own size; it then streams that screen like any other and what it sends to that screen (keys, mouse) lands on that one window. It adds no permission, no listening port and no packet type (it is three actions of the virtual-screen packet, `list`, `lend` and `return`, behind the same Input gate), and it moves nothing else: the window id must be digits (Sway's container id) or `0x` and hex (Hyprland's address), the only strings that reach a Sway command or a line of Lua, and the output and workspace names that do are checked to be plain ASCII with no quote, backslash, semicolon or comma. **What it costs:** while a window is lent it is off your screen and its picture is on the other computer, so whoever uses that computer sees what the window shows and can type into it (a terminal or a browser logged in as you included), exactly as with "Show its screen" with control, but for one window and without your seeing it here. The other computer can learn what is open (its window list, from `list` and the one the phone's window picker already gets, includes the titles of every window here; the titles are sent, never logged, and kept on the asking computer (owner-only, in its `computers.json`) only while the app's picker is open: the picker asks for the list to be cleared as it closes, and the server drops a list nobody asked for again within a minute and any a stopped server left at its next start, so a quit or crashed app does not leave them behind for longer) and borrow any of them, up to the four-screen limit, one after another; it cannot lend a window that is lent to another, and a phone, a computer paired one way, a guest or a time-limited device can never do it. **How it ends:** by the borrowing computer's `return`; by that computer having no session, connection or link (noticed within a second or two while a window is lent), or having no session capturing that window's screen for a minute (a `return` lost on a link that stays up does not strand the window; the virtual screens' 5-second sweeps stay the backstop); by the server stopping; and, after a crash or kill, at the next server's start in the same compositor (`lent_windows.json` holds what was lent and from where, written before the window moves); turning the switch off stops the list and new lends and puts every lent window back within a second or two. A window closed while lent has its empty screen removed within a couple of seconds, and the borrowing computer is told so its view ends. **A limit of the putting back:** a tiled window returns to its workspace but at the end of its layout, a floating one to its recorded place; if its workspace or output is gone the compositor places it. **Not yet checked on a real desktop:** the live test ran in a throwaway headless Sway and a Hyprland 0.56.2 nested in the laptop's session, never with a real second computer or a window the owner cares about (device checklist section 269).
87. **A computer of yours whose keyboard and mouse are on this one can make this computer open a window of its own** (window handoff phase 4, "Drag windows to my other computers", `drag_windows_across`, **off by default**, a Setting of the computer the window leaves; Sway and Hyprland). **What it adds:** the offering computer sends one packet of the virtual-screen type with no action (`{drag_window: …}`, docs/protocol.md), and this computer asks its app to open a borrowed window of that computer's window, which then asks `lend` as "Borrow a window" does under limit 86 (so it needs that computer's `lend_windows` on, and shows only a window it lends). It adds no permission, port or packet type. **Held to:** the packet is taken only from a computer paired both ways ("both are mine", its grant neither pending nor lapsed) **and** only while that computer's keyboard and mouse are on this one (the computer driving it), at most one in two seconds from each computer, only while this computer's own `drag_windows_across` is on, never on Windows, and every field is checked as an ask is (a window id that is digits or `0x` and hex, a place and a size a screen can have, a title without control, bidirectional or other format characters and cut at 200; the request the app takes is held to the same again, has a file of its own so another cannot overwrite it, lives ten seconds, and is removed as it is read). The offering computer is told with an answer whether it was taken, so it never believes it handed over a window that was dropped. A phone, a computer paired one way, a stranger or a computer whose pointer is not here is dropped with a line at debug in the log, never a title. **What it costs:** whoever controls that computer's keyboard and mouse can already type here (limit 59); this lets the same hand put one more window of that computer on this screen, a window that computer chose to lend, which is no more than "Show its screen" of it. **What the offering side reads:** it reads its own compositor's window list and focus (Sway's tree, Hyprland's `j/clients` and `j/activewindow`) when a drag ends, and the lend moves nothing until the other computer asks; its list of windows handed over is in memory only, ends with each lend and is kept at most an hour. A window is taken home by a drag back only when the computer it was lent to says its own view of that window has the focus (the computer asked is one of this one's own, as for a lend), so no other drag, a text or a file or another window, moves it. **Not yet checked on a real desktop:** two real computers, and Hyprland 0.56's input capture with a button held (device checklist section 279).

88. **On Windows, the same lending (limit 86) leaves the window on the desktop and lets the other computer click and type into it there** (window handoff phase 5, the same `lend_windows` switch, **off by default**). **What it adds:** nothing to who may ask (a computer paired both ways, with Input, while the switch is on) and no packet type. A lent window is not moved to a hidden screen (Windows has none without a display driver): it stays where it is, its owner sees it, and what the other computer sends lands on that window through the real pointer and keyboard (`SendInput`), after the window is brought to the front. **What it costs, beyond limit 86:** the borrowing computer moves and clicks this computer's real pointer inside the window's frame, so the owner's own use of the pointer and keyboard competes with it; a window it covers is covered (the lent window is raised); a window that was minimised after the lend is restored, a window may be resized to the borrowing window's size (never one that is maximised or minimised; one that grows is moved back onto its screen) and is put back as it was (show state and place) on return. **How a borrower is confined to the one window** (what it can and cannot do): only a window the list shows can be lent, however its handle is named (never the desktop, the taskbar, the shell's own surfaces, this program's own windows, or a program with more rights than this server); the window is lent to one device, and only a session of that device (the id the pairing check judged against the key its connection proved) is given its capture index, any other paired device is refused; every session holds a lease on that exact lend and, when the window is returned, swept, closed, lent again or its handle names another window, it ends within a moment and sends nothing more (an index freed is not handed out again at once, and a new lend never shares a lease with an old one); the pointer is placed only inside the window's visible frame and only where that window, not one covering it, takes the click; a click or scroll goes to the last place the viewer pointed in the window; a click, scroll, key or text is sent only while the window (or a dialog it owns, of the same program) is in front: it is raised once if not, and the packet is dropped if that fails, and any key or button the session held is let go; keys are an allow-list (letters, digits, punctuation, editing, arrows, function and keypad keys, modifiers), never the Windows key, Alt+Tab, Alt+Esc, Ctrl+Esc, Ctrl+Shift+Esc, print screen, media, volume or power keys; the gamepad, the laser dot, moves by a distance, the phone's mic and the computer's sound are dropped; a window's handle is never followed alone (its program and thread must match, so a recycled handle is never moved, sized, restored or driven). **What is not closed:** the checks run just before the input is sent, not at the same instant, so a window that comes in front, or the owner's own hand moving the pointer, in that gap can take an event; the injector rounds a place to a pixel, so a point on the very edge of the frame can land a pixel off; the trust in the device id is the device keys' (a device whose key was never bound is bound by its first session); a device that has Input and does not use a lent window can still open an ordinary screen session, as it could before; and a shell surface whose class this server does not know as the shell's would be listed like any window. **What is kept:** the lent windows and where they were are kept in memory only (a window handle is not kept across a restart), so a server that crashes while a window is lent leaves it at the size the other computer last gave it; a clean stop puts every window back. **Not yet checked on a real Windows desktop:** every live part (device checklist section 280).
89. **On GNOME, the same lending (limit 86) shows one window to the other computer and lets it do nothing to it** (window handoff phase 6, the same `lend_windows` switch **and** `gnome_unattended`, both **off by default**). **What it adds:** nothing to who may ask (a computer paired both ways, with Input, while both switches are on) and no packet type. A lent window is not moved: it stays on its desktop and mutter's own `org.gnome.Mutter.ScreenCast` `RecordWindow` is asked for a stream of that window by id, the same no-dialog D-Bus path as limit 75 (any program of yours on your session bus can make the same call; a window's id is not guessable, and GNOME Shell gives the list of ids to its own apps only). **What it costs:** whoever uses the other computer sees what the window shows, its title in the picker, and anything it shows while it is lent (the stream is of the window, not of the screen); the owner's pointer is not in it; GNOME is asked to show its screen-sharing indicator (`is-recording`) while it runs. **What it cannot do, held by construction:** a session on a lent GNOME window sends no input of any kind (`window_target::takes_input` is false for it, so the session is view-only before it starts: its ready stream says so and every input packet is dropped, and the window guard that would place input has no answer to any of its questions off Windows and drops all). That is deliberate and measured: mutter's RemoteDesktop would clamp a pointer position to the window's rectangle but send the click to whichever window is topmost there (a click aimed through the lent window's stream landed in the window that covered it), and a key goes to the window with the keyboard; no program can ask GNOME which window covers a spot or has the keyboard. The grant is the Windows one: one window to one device, a lease per session that ends within a moment when the window is given back, closed, swept or lent again, only a window the list shows (not this program's own, not a hidden one) may be lent whatever id is named, the id must be plain decimal digits, and a session is refused unless its device is the one it was lent to. **What stops it on stock GNOME:** GNOME Shell refuses `Introspect.GetWindows` to any caller that is not one of its own apps (measured: "Access denied"), so no window is listed or lent; nothing here tries to get round that (no guessing of ids, no impersonating an allowed caller, no unsafe mode). **Not closed:** the lease does not compare a program and thread as the Windows one does (mutter never gives a window id to another window, which is why it need not); the server ends the grant when the window has been gone for two looks, and the stream ends with the window. **Not yet checked on a real GNOME desk, or with a Shell extension:** device checklist section 281.

## Using it safely today

- **If you turn on "Separate windows (Shizuku)" (limit 83),** do it only on a phone and a computer you control, and only if you already run Shizuku; every window shows and takes what its app does, and the phone's lock does not close one that is open, so close them, or turn the switch off, when you leave the computer. Nobody needs wireless debugging for this, and nothing else in Pocketdesk asks for Shizuku.
- **If you turn on "Let my computers turn on my hotspot" (limit 85),** do it only on a phone and a computer you control, with a strong hotspot password set in Android: while it is on, anyone in range with that password uses your mobile data, and the computer (or anyone using it) can turn it on even while the phone is locked. Leave the auto-off on (a hotspot Pocketdesk turned on goes off after 4 hours at most, whatever you choose). Nobody needs wireless debugging for this.
- **Use Tailscale, or another VPN, anywhere you do not trust everyone on the network.** It closes the limits above for traffic between your own devices.
- **Keep `pairing_required = true`.**
- **If you make a direct link (limit 77),** show its code only to the phone you mean, turn it off when the session is done, and close your firewall on the interface it makes if this computer listens on anything you would not share with a stranger. Turn "Offer a direct link" off if you never want this computer to be an access point.
- **If you turn on "Unattended on GNOME" (limit 75),** do it only on a computer where a paired phone showing the screen with no one there is acceptable, and watch for GNOME's screen-sharing indicator in the top bar while a phone is connected.
- **If you set up a spare phone as the wake helper (limit 82),** keep it on a charger at home and out of other people's hands, pair it with this computer's own code (so it is one of yours), and turn the switch off, unpair it and remove it in Settings, Wake, if it is lost. If one of your other phones is lost, remove it from the Devices page: the helper drops it within about 15 seconds while linked to the computer.
- **If you use "Location from my phone" (limit 76),** leave the precision at City unless an app truly needs more, give "Exact location" on the phone only then, and turn the setting off when you share this computer with users or programs you do not trust: each of them can read the place through GeoClue while it is on.
- **If you use "Drag windows to my other computers" (limit 87),** leave "What starts a window drag across the edge" on "Super or Alt held with the button", so only a deliberate move takes a window, and know that the window you drag is the one in front when you cross, a floating one under the pointer.
- **If you use "Watch controls" (limit 84),** leave Deck off unless you want a watch's deck buttons to run tasks on the computer, set a lock on the watch (a deck button and a No refuse without one), pair only with the pairing screen open and only with digits your own watch shows, and "Forget" the watch on the phone if it is lost; it cannot say Yes to a question, so keep the fingerprint on the phone for those.
- **If you use "Approve with my phone" (limit 73),** add only the `auth sufficient` line Settings shows, keep a root shell open while you try it, pin with attestation (never `--pin-without-attestation` unless the phone has none), check every digit of the key it prints, turn on "Fingerprint only, not the PIN" on the phone if others know its PIN, and answer No to any request you did not make.
- **If a phone or computer of yours is lost or stolen, remove it at once:** its computer's Devices page Unpair, or from another of your devices, Devices there… (or the phone's Devices on this computer). While it stays paired, an owner device can remove your other devices from its computers (limit 71).
- **If your computers are not equally safe** (one lives at work, or others use it), turn "Let my computers add my phones here" off on the others (limit 72), or do not pair them both ways; and when you unpair one, unpair the phones it added too.
- **On a shared network,** turn on "Ask before each session" for your phones, and grant each phone only what it needs.
- **Keep the control and stream ports closed to the internet.** The WAN path (iroh) does not need them open.
- **Pair by scanning the QR code** rather than typing an address. It pins the right computer before the first connection.
