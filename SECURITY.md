# Security

Pocketdesk lets a phone see and control a computer, so what it protects, and what it does not yet protect, matters more than its feature list. This page describes the design as it is in this tree, including its limits.

**Two things to know before you pair.** Pair by scanning the desktop app's QR code: typing an address, or picking a computer found on the network, trusts whatever answers there first (limit 1 below). And the internet path is always on: relays see both ends' IP addresses, which endpoints talk and how much, and the Mainline DHT links the computer's WAN id to its home IP, and the phone's IP to the id it looks for (limit 4), unless `dht_publish = "off"`. None of it needs a port forward, except waking a sleeping computer from outside and running your own relay.

## Reporting a vulnerability

Please report security problems privately. Use GitHub's **Security → Report a vulnerability** on this repository, which opens a private advisory only the maintainer can see. Do not open a public issue. Include what you found, how to reproduce it, and what an attacker gains.

## The connections and what protects them

| Connection | Port | Encrypted | How the peer is identified |
|---|---|---|---|
| Control channel (pairing, clipboard, file browse, notifications, commands) | TCP 1716 | Yes (TLS 1.3) | Both ways by key, as on the stream: the phone pins the desktop's certificate, and must present its own, which the desktop holds the device to (device keys). A client that does not speak TLS is refused |
| Video, audio and input stream (LAN) | UDP 4716 (QUIC) | Yes (TLS 1.3) | Both ways by key: the phone pins the desktop's certificate (first use, or the QR code's fingerprint) and checks the handshake signature; the phone presents its own certificate, and the desktop holds the device to it (device keys) |
| Stream over the internet (WAN) | iroh (QUIC) | Yes | Both ends' iroh keys; the desktop holds the phone to the iroh key it registered on the LAN |
| Control channel over the internet, when TCP 1716 cannot be reached | iroh (QUIC) | Yes | Both ends' iroh keys. Only a paired phone whose iroh key was registered on the LAN; nothing pairs over it. File transfers ride streams the computer opens on it (`internet_files`, on by default), held to the same keys, with no TLS layer of ours and no connection back to the phone |
| File transfers | a fresh TCP port per file | Yes (TLS 1.3) | Each end accepts exactly one certificate: the phone, the desktop it pinned for the address it asked; the desktop, the key bound to the phone that asked. A one-time key per transfer is checked inside, and the desktop dials only the address the request came from |

Tailscale, when you use it, wraps all of these in WireGuard, which encrypts and authenticates the whole path between your devices.

## What is protected

- **Pairing:**
  - A 6-digit PIN is valid for 5 minutes and pairs one phone. A PIN that paired stays spent even if its file cannot be deleted, and a PIN file without its minting time is no PIN.
  - It is discarded after 5 wrong guesses, and the desktop shows at most one new PIN every 10 seconds.
  - It travels inside TLS. With the QR code, the phone checks the desktop's certificate before the first byte, so the PIN reaches only that computer.
  - With `pairing_required = true` (the default), an unpaired device may only pair, on the control channel, and is refused on the stream.
- **The desktop's identity:**
  - The phone pins the desktop's certificate, on the stream and the control channel alike, and checks that the desktop holds its key.
  - A pairing code can never replace a certificate the phone already trusts for an address.
- **The phone's identity (device keys):**
  - Pairing binds the phone to the certificate it proves on the connection that pairs. The first LAN stream it then opens registers the iroh key it names there for the WAN. A WAN stream never binds a key by itself.
  - From then on, a connection that claims to be that phone with any other key, or with none, gets nothing: the stream is refused, the control channel may only pair again, and the desk is notified.
  - Each control connection is known by the id it opened with, and held to its key on every packet: pairing or unpairing (the command or the desktop app's Unpair) applies at once to connections already open.
  - Pairing again with the desktop's own PIN binds the phone's new key (a phone whose certificate changed recovers this way). `pocketdesk unpair` and the desktop app's Unpair clear the keys.
  - A guest PIN binds only an id that no phone holds. It can never take over, or extend, a paired phone's id.
- **Per-device permissions:**
  - Each paired phone can be limited to view-only, and denied the clipboard, files, sound, the microphone, power actions or commands.
  - Running commands is off until granted.
  - "Ask before each session" holds every session for that phone until someone at the desk allows it.
  - The server re-reads them each second for running sessions: a phone that is no longer paired (unpaired from the CLI or the app, an expired guest grant), or whose Input, Sound or Microphone was turned off, loses its session within a second, whatever made the change.
  - Privacy mode belongs to the phone that turned it on: no other phone can refresh or end it, and it ends once that phone is no longer paired.
- **Abuse by a connection:**
  - A control packet is at most 4 MiB, on both control channels: a longer line ends the connection, before anything is buffered past that.
  - The control and stream ports hold at most 8 connections from one address and 128 in all; more are refused. The stream port counts an address only once it has answered a QUIC Retry, so a forged source address cannot use up a phone's share. The internet (WAN) listener holds at most 128 in all.
  - One phone runs at most two file transfers at a time, within the desktop's four.
  - A device id must be printable (no control or invisible formatting characters) and at most 128 bytes, on the control channel, the stream and the v2 handshake. A device's name is held to one printable line of at most 40 characters (`clean_device_name`): cleaned where it is kept, refused in the v2 handshake when it is not already so.
  - A folder listing fits in one packet: a huge folder is listed in part, and the phone says so.
  - Refusals are logged: the first on each connection at the default level.
- **Files:**
  - Transfers run inside TLS, pinned both ways: no other device can read the bytes, send them, or take them.
  - A paired phone moves files only once its key is bound (pairing binds it).
  - Received files are confined to one folder: Downloads, or the folder the owner chose (C2, desktop Settings "Received files land in"), never Pocketdesk's own state or config folders. They never overwrite anything, are size-limited, and are marked as downloaded on Windows. A phone with Files can fill whatever folder the owner chose, as it could Downloads.
  - Browsing and downloading are confined to the home folder. Hidden files, the server's own keys and settings, network paths and device names are refused, and links that lead out of home are refused too.

## Known limits

These are real gaps in the current design. Plan around them.

1. **Without the QR code, the first contact with an address is trust on first use.** Someone who can intercept that very first connection could relay the pairing. Scanning the QR code closes this.
2. **A phone paired before device keys, that has not streamed on the LAN since, holds no key yet.** Until it does, the control channel accepts it by its id alone, and it moves no files. The first LAN stream the desktop allows binds its key, and pairing it again binds it at once.
3. **Someone who knows an unpaired phone's id can get in the way of its pairing**, by asking for PINs or spending the wrong guesses under that id. They cannot pair as it without the PIN.

4. **The Mainline DHT links the desktop's WAN id to its home IP** (roadmap N3), unless `dht_publish = "off"`.
   - The record is public to anyone who knows the id. By default it holds the relay URLs, which name your own relay when you run one. With `"addresses"` it also holds your home's public IP addresses.
   - In every mode, the DHT nodes that store the record see the home IP it was published from, hourly, so the id can be followed to the home over time.
   - A phone's WAN dial asks the DHT for the id, which shows strangers' nodes the phone's IP and the id it is looking for.
   - The id is in the pairing QR code, on each paired phone and on every relay the desktop uses. A forged record gets nowhere: it is signed, and the phone checks the desktop's key again when it connects.
5. **The connection limits are shared.** Phones behind one public address (carrier NAT, or a forwarded port) share that address's 8 connections, so one can use up the others'. Anyone who can reach the internet listener can hold its 128 until each handshake times out; the gate still refuses them.
6. **Privacy mode is held to its phone's id, as strongly as that id is held to a key** (limit 2). If that phone's Power permission is turned off, it cannot end the grab and no other phone may, so the local keyboard and mouse stay blocked until it expires (10 minutes).
7. **The desktop names itself to anyone who connects.** Any client that completes the TLS or QUIC handshake, with any certificate, gets the desktop's device id, name and plugin list before it is judged, and its certificate. Anyone on the network sees the same id and name in the mDNS announcement unless `lan_discovery = false`.
8. **The permissions limit what a phone may ask for, not what the desktop tells it.** A paired phone with every permission off still receives the desktop's notifications, its window titles (window list and workspace HUD), its battery, the wake details (the MAC) and the internet endpoint. Unpair a phone to stop them. The clipboard is the exception: the text you copy is pushed only to phones with Clipboard on, and with "Clipboard to phones" (`clipboard_push`) off, to none, though a phone in a session can still ask for it. A copy a password manager marks private (on Windows the formats that keep it out of clipboard history; on Wayland `x-kde-passwordManagerHint`) is never pushed, but other copied secrets reach every connected phone with Clipboard on. The phone's "Computer's clipboard in the background" decides only whether the text is put on its clipboard: the phone receives it while its link is up either way.

9. **A phone with Links on can open web pages in this computer's browser** (roadmap T8a), up to 5 a minute, without asking, including pages on your home network such as a router's. Only `http` and `https` links go either way, never one to the computer's own loopback (`localhost`, 127/8, `::1`, in any spelling a browser reads as one) and never one with a user name or password. Links is on for every paired phone and guest by default, as Input is, and a phone with Input can type the same link. Turn Links off per phone in the Devices tab, or set "Links from phones" (`open_links = false`) to have links shown instead of opened. On the phone, any app can share a link to "Open on computer"; it goes to the last computer used.

10. **A phone with "My media on the computer" on tells the computer what it plays** (roadmap T8d): the title, artist and app, kept owner-only in the state folder while it is connected. The computer, with that phone's Media permission on, can pause and skip it. Both sides must agree: the phone's setting (off by default) and the desktop's Media switch.

11. **With "Names from my contacts" on, the phone tells its computer who texts it** (roadmap T8e): the sender's name from the phone's contacts goes with each forwarded text and is kept owner-only in `sms.json` (turning `sms_names` off forgets the kept names at the next start). A name says what the phone's contacts call that number; a text's sender number can be spoofed, so a name is not proof of who sent it.

12. **With "Let the computer answer notifications" on, the computer can act as you in the phone's apps** (roadmap T10c): it can press a notification's buttons (up to three, by title, never one Android runs only once the phone is unlocked) and reply to a chat, from the desktop app's Notifications page or, since N3, from the notification itself (a Windows toast's buttons and reply box; a Linux notification's actions and KDE's inline reply), at most 10 a minute. A toast can pop up under the cursor while you work, so one stray click presses whatever the phone's app offered ("Delete", "Archive"); desktop Settings "Answer in the notification" (`toast_answers`) turns that path off and leaves the Notifications page. Only a notification sent in full (not one whose content the lock screen hides, nor one carrying a code), and only from the phone's own computer. The notifications that can be answered are kept owner-only in `phone_notifications.json` while the server runs. It is off by default, and the desktop's Notifications switch for the phone turns it off too.

13. **The folders a phone shares (roadmap T10g) can be read by its computer.** In the desktop app's Phone tab, or by anything running as you that writes its requests, the computer lists them and copies any file in them, hidden ones (a leading dot) left out. Only folders the phone's owner picked in Settings, "Folders the computer may open", and only from that phone's own computer, with its Files permission on. Removing a folder there gives its grant back.

14. **With "New screenshots to the computer" on (roadmap T10h), every screenshot taken on the phone goes to its computer**, whatever it shows: onto the computer's clipboard and into its Downloads. On the computer it is then in the clipboard's history (Windows' Win+V, and its cloud clipboard if that is on) and in Downloads. Only to the phone's own computer, only images in a folder named `Screenshots` (an app that drops other images there sends them too), at most 10 minutes old; the computer's Clipboard and Files permissions gate each half. It is off by default.

15. **A phone's cast shows everything on its screen on the computer** (roadmap T10k), notifications and codes included, to whoever sees the computer's screen, while the phone's owner casts it. Android asks for consent each time, and its status bar shows that the screen is shared. The computer hands the picture from the server to the desktop app over loopback TCP, behind a token only its owner can read (`cast.json`); any program running as that owner can read the token, and so watch the cast. The Cast permission ("Show its screen here", on by default) refuses it per phone.

16. **The event log and hooks keep a record of what happens, and run what you tell them** (ecosystem phase 1a). `events.jsonl` in the state folder (owner-only, 1 MiB and one older file kept) lists sessions, phones linking, batteries, and the notifications, texts, files and links that arrive. By default it records only who, when and how much: the app a notification came from, a file's size, a link's host. With "details in events" on (`events_detail = "full"`) it also keeps their content (notification and text bodies, senders, file names, whole links), on disk, until the log rotates. A hook in `[hooks]` runs as you, with the event on stdin and in `POCKETDESK_EVENT`, through the shell: treat the event's fields as untrusted text (a phone chooses a notification's text and a file's name), and read the event from stdin: on Windows `%POCKETDESK_EVENT%` in a hook's command line is expanded before cmd parses it, so a phone-chosen field could run commands. A hook is stopped after 30 s, but programs it started in the background may go on. Turning "Event log" off writes nothing; hooks still run.

17. **A phone with the Tasks permission can run the commands you named as tasks** (ecosystem phase 1c), as you, through the shell: only those, by name, never a command of its choosing (that is Exec, off by default). "Ask first" is on for a new task, and holds each start for your Allow in the desktop app (a minute, then denied); turn it off only for a task that is harmless whenever it runs. Tasks is on by default for every paired phone and guest grant, like the other permissions but Exec, but nothing runs until you name a task. A run stops at its time limit (60 s unless you set another, at most an hour), though programs it starts in the background may go on. A phone may ask for 10 starts a minute, and a start that asks first holds one of the 2 places while it waits for you (up to a minute), so a paired phone can keep your other tasks waiting and keep asking.

18. **The browser extension can make this computer send a page, a link or an image to your phone** (ecosystem phase 1d), when you right-click one: the browser starts `pocketdesk browser-host` as you, and only the Pocketdesk extension's id may talk to it. For an image, Pocketdesk downloads the address itself (`http`/`https`, never the computer's own `localhost`, the address and each of at most 5 redirects alike, though a name that resolves to an address on your network is not refused; at most 32 MB, only a PNG, JPEG, GIF, WebP, AVIF or BMP by its content type, and named for that type: an address ending `.apk` arrives as a `.png`; SVG is not sent), so the site sees this computer fetch it, not the browser. The phone's Links and Files permissions apply. Another extension cannot reach the host, but anything running as you could run it, as it could any of your programs.

19. **Home Assistant sees your computer and phones, and can start your tasks** (ecosystem phase 1e), when you turn it on and name an MQTT broker. The server publishes, retained: whether it runs, the number of sessions, whether a phone's screen is shown, each paired phone's battery and connection, and your tasks' names (never their commands). Not retained, as they happen: each event's kind and phone, so the broker learns that a notification, a text, a file or a link arrived and from which phone (by the first 8 characters of its id), never what it said or was called. The connection is plain MQTT, so anyone on the network path can read it and the password, and anyone the broker lets publish to `pocketdesk/<computer>/task/…/run` can press a task's button: a task that asks first still waits for your Allow at the desk, but one that does not ask runs. Give the broker a password, keep it on your own network, and leave "ask first" on for any task you would not let your broker start. The password sits in config.toml, which Pocketdesk writes readable only by you; a config.toml you wrote by hand keeps the permissions you gave it until Settings saves it. Turning the bridge off marks the entities unavailable in Home Assistant; delete the device there to remove them.

20. **With "Tell other apps what happens" on, any app on the phone learns when you use Pocketdesk** (ecosystem phase 1f): the broadcasts name no app, since an automation app cannot hold a permission of ours, so any app may hear when a session starts and ends, a file or link arrives, files finish sending or a task ends, with the computer's saved address, a file's type and size, and a task's name and exit code. Never a file's name, a link, a task's output or a notification. Any app can also send the same broadcasts, so an automation should not treat one as proof that it happened. Off by default.

21. **Another of your computers, once paired, may do what a phone with Clipboard, Files and Links may** (ecosystem 2f, 2g): browse and fetch files under your home folder, send links that open in your browser, and, with "Clipboard with my computers" on on both, share the clipboard both ways (text; a password manager's private copies stay where they are). It may not send input, sound, power or commands, and a screen session from it is held for you to allow. Pairing it takes your PIN, inside the pairing link that the Pair tab copies, so treat that link as the PIN: Pocketdesk never sends a pairing link from the clipboard to a phone or a computer, but it stays on this computer's clipboard (and in Windows' clipboard history) until you copy something else; its certificate is pinned from the link before the PIN is sent. Unpairing on one computer does not unpair it on the other: unpair it in the other's Devices page too. The link between them rides the internet path (iroh), so relays and the DHT see what they see for a phone (the start of this page, and limit 4). A computer running a Pocketdesk from before this pairs the other as a phone, with a phone's default permissions: update both first.

22. **KDE Connect devices can find this computer and connect to it, on by default** (ecosystem 3a; desktop Settings "KDE Connect devices" turns it off). The desktop app's "Find KDE Connect devices" broadcasts this computer's name and a KDE id of its own on the local network; a device that hears it (or knows the address) dials the control port. That path takes TLS 1.2 as well as 1.3, since KDE Connect Android caps at 1.2, and holds a device to the id its certificate names; the Pocketdesk road stays TLS 1.3 only. A device that has not paired is given nothing (at most 4 such links from one address, closed after 5 silent minutes, one pairing request at a time each). Pairing (3b) is held for you with a code both screens show, either way: a device's request waits for your Allow, and a device's acceptance of yours waits for your Confirm. **The code is the only check**: any device on the network can ask, under any name, and can claim a device's id while that device is not connected, so compare the code on both screens before you answer, and do not answer a request you did not expect. Your answer names the code you saw, so it is not taken for a request made since. Once paired, a device reconnects only with the certificate it paired with, and may do only what its own switches allow (3c), narrower than a phone's: ping; its battery; the clipboard both ways (your copies go to it while "Clipboard to phones" is on); being rung from here; and, only when you turn it on, sending files into Downloads (fetched from the device's own address, held to its paired certificate, marked as downloaded); and its notifications (N9, on by default, sent only with notification sync on in its own KDE Connect app), **shown here in full**: unlike Pocketdesk's phone app, which keeps lock-screen-private content and one-time codes off the computer, KDE Connect sends what it sends and this computer cannot tell what is private, so the text reaches the toast, the notification centre and, with "details in events", the event log and hooks; turn the device's "Show its notifications here" off, or choose apps in its KDE Connect app. Nothing else it sends is taken, Pocketdesk's own packets among them. A file stops on the way if you unpair the device or turn Files off, and a device sends at most 4 at once.

23. **Your computer can ring a paired phone loudly** (N1): its Ring button or `pocketdesk ring` make the phone ring for 30 s at its alarm stream's full volume (at the owner's alarm volume on Android 17 and newer, where an app may not raise it from the background), through Do Not Disturb when alarms may sound. Only a paired phone with its Ring permission on (Devices) and its own "Ring from the computer" on, or a session or the remote open, rings; at most once a minute, and never another computer. Anyone who can use the owner's account on the computer can therefore ring the phone.
24. **With "Remember the screen-sharing grant" on, sessions start with no one at the computer** (N8; GNOME and KDE, off by default): the portal's grant to share the screen (and, where input goes through the portal, to drive the keyboard and pointer) is kept until revoked, with its restore token owner-only in the state folder (`portal_restore_token`, `portal_remote_token`). Anyone who can read your state folder can start a screen share as you, without asking; every session is still held to a paired phone, its key and its permissions, and "ask first" where set. Revoke it in the desktop's own privacy settings (GNOME: Privacy, Screen Sharing; KDE: the portal's permissions). Forget the grant in the app, or turning the setting off, only drops the local token, so the next session asks again; the desktop's own permission stays until revoked there.
25. **With the phone's "Let the computer control this phone" on, the computer it shows its screen to can act on it** (C8; off by default, and it needs an Accessibility service the owner turns on in Android's settings).
    - **What it can do:** only during a cast, and only from the computer the phone itself opened the cast to, that computer can tap, drag, scroll, type into the focused field, and press Back, Home, Recents and the shade. Nothing is touched or typed while the phone is locked, so the computer cannot enter its PIN or pattern; Back and Home still go.
    - **On the computer:** any process running as the owner that can read the cast's token (`cast.json`, owner-only) can send control. The desktop app's "Control phones from their screen window" is the app's own choice, not a gate the server enforces. The phone's setting is the real gate.
    - **What Android allows:** the service may read the screen. Pocketdesk reads only the field it types into and sends nothing it reads.
    - **Advanced Protection:** Android 17's Advanced Protection does not allow the service.

26. **With the phone's "Recent photos on the computer" on, its computer can see its newest camera photos** (C7; off by default, and it needs photo access). The computer asks; the phone answers its own computer only, with thumbnails of at most 24 photos in DCIM, and sends a full photo only when asked, through the usual transfer. The thumbnails are kept owner-only in the computer's state folder, so anyone who can read that folder, or use the owner's account on the computer, can see them; turning the switch off on the phone stops further answers, and they are dropped when the server starts again.
27. **With the phone's "Let the computer mute this phone" on, its computer can turn on its Do Not Disturb** (D2; off by default). The computer asks with a number of minutes, at most a day; the phone takes it only from its own computer, only when it is not already quiet, and ends it at its time unless the owner changed it meanwhile. Meanwhile calls and messages the owner's own Do Not Disturb settings let through still come, but others are silenced: anyone who can use the owner's account on the computer, with the phone's Mute permission on (Devices), can quiet the phone for up to a day at a time. The phone also tells that computer whether it is in Do Not Disturb, which says something about the owner's day.
28. **With "Clipboard history" above 0, the computer keeps in plain text what crossed** (D3; off by default). The last texts that went between this computer and its phones, either way, sit in `clip_history.json` in the state folder, owner-only, until they fall off the end, the history is cleared, or it is turned off. A copy a password manager marks private never crosses and so is never there, but a secret copied without that mark, or one the phone's tile sent after you confirmed it, is; so is a KDE Connect device's text. Anyone who can read your state folder, or use your account on the computer, can read them. A pairing link, anywhere in a copy, is never kept.
29. **With "Let the computer answer notifications" on, a chat's recent messages reach the computer** (D4). For a chat notification sent in full, its newest ten messages, other people's names and texts included, go to the computer, where they are kept owner-only with the notification (`phone_notifications.json`, the newest 30). A thread in which any message looks like a one-time code is not sent. Anyone who can read your state folder, or use your account on the computer, can read them; turn answering off in the phone's Settings to keep them on the phone.

## Using it safely today

- **Use Tailscale, or another VPN, anywhere you do not trust everyone on the network.** It closes the limits above for traffic between your own devices.
- **Keep `pairing_required = true`.**
- **On a shared network,** turn on "Ask before each session" for your phones, and grant each phone only what it needs.
- **Keep the control and stream ports closed to the internet.** The WAN path (iroh) does not need them open.
- **Pair by scanning the QR code** rather than typing an address. It pins the right computer before the first connection.
