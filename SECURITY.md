# Security

Pocketdesk lets a phone see and control a computer, so what it protects, and what it does not yet protect, matters more than its feature list. This page describes the design as it is in this tree, including its limits.

**Two things to know before you pair.** Pair by scanning the desktop app's QR code: typing an address, or picking a computer found on the network, trusts whatever answers there first (limit 1 below). And the internet path is on by default: relays see both ends' IP addresses, which endpoints talk and how much, and the Mainline DHT links the computer's WAN id to its home IP, and the phone's IP to the id it looks for (limit 4), unless `dht_publish = "off"`. None of it needs a port forward, except waking a sleeping computer from outside and running your own relay. "Reachable from the internet" in the desktop's Settings (`internet_path = false`) turns the whole path off: no relay or DHT is contacted, phones reach the computer on the same network or through Tailscale only, and your other computers do not link with it.

## Reporting a vulnerability

Please report security problems privately. Use GitHub's **Security → Report a vulnerability** on this repository, which opens a private advisory only the maintainer can see. Do not open a public issue. Include what you found, how to reproduce it, and what an attacker gains.

## The connections and what protects them

| Connection | Port | Encrypted | How the peer is identified |
|---|---|---|---|
| Control channel (pairing, clipboard, file browse, notifications, commands) | TCP 1716 | Yes (TLS 1.3) | Both ways by key, as on the stream: the phone pins the desktop's certificate, and must present its own, which the desktop holds the device to (device keys). A client that does not speak TLS is refused |
| Video, audio and input stream (LAN) | UDP 4716 (QUIC) | Yes (TLS 1.3) | Both ways by key: the phone pins the desktop's certificate (first use, or the QR code's fingerprint) and checks the handshake signature; the phone presents its own certificate, and the desktop holds the device to it (device keys) |
| Stream over the internet (WAN) | iroh (QUIC) | Yes | Both ends' iroh keys; the desktop holds the phone to the iroh key it registered on the LAN |
| Control channel over the internet, when TCP 1716 cannot be reached | iroh (QUIC) | Yes | Both ends' iroh keys. Only a paired phone whose iroh key was registered on the LAN; nothing pairs over it. Another of your computers dials it with its own ALPN, `pocketdesk-computer/1`, which only picks the congestion controller: it is held to the same keys and checks, and is let in no further. File transfers ride streams the computer opens on it (`internet_files`, on by default), held to the same keys, with no TLS layer of ours and no connection back to the phone |
| File transfers | a fresh TCP port per file | Yes (TLS 1.3) | Each end accepts exactly one certificate: the phone, the desktop it pinned for the address it asked; the desktop, the key bound to the phone that asked. A one-time key per transfer is checked inside, and the desktop dials only the address the request came from |

Tailscale, when you use it, wraps all of these in WireGuard, which encrypts and authenticates the whole path between your devices.

## What is protected

- **Pairing:**
  - A 6-digit PIN is valid for 5 minutes and pairs one phone. A PIN that paired stays spent even if its file cannot be deleted, and a PIN file without its minting time is no PIN.
  - It is discarded after 5 wrong guesses, and the desktop shows at most one new PIN every 10 seconds.
  - It travels inside TLS. With the QR code, the phone checks the desktop's certificate before the first byte, so the PIN reaches only that computer.
  - With `pairing_required = true` (the default), an unpaired device may only pair, on the control channel, and is refused on the stream.
- **The desktop's identity:**
  - The phone pins the desktop's certificate, on the stream and the control channel alike, and checks that the desktop holds its key.
  - A pairing code can never replace a certificate the phone already trusts for an address.
- **The phone's identity (device keys):**
  - Pairing binds the phone to the certificate it proves on the connection that pairs. The first LAN stream it then opens registers the iroh key it names there for the WAN. A WAN stream never binds a key by itself.
  - From then on, a connection that claims to be that phone with any other key, or with none, gets nothing: the stream is refused, the control channel may only pair again, and the desk is notified.
  - Each control connection is known by the id it opened with, and held to its key on every packet: pairing or unpairing (the command or the desktop app's Unpair) applies at once to connections already open.
  - Pairing again with the desktop's own PIN binds the phone's new key (a phone whose certificate changed recovers this way). `pocketdesk unpair` and the desktop app's Unpair clear the keys.
  - A guest PIN binds only an id that no phone holds. It can never take over, or extend, a paired phone's id.
- **Per-device permissions:**
  - Each paired phone can be limited to view-only, and denied the clipboard, files, sound, the microphone, power actions or commands.
  - Running commands is off until granted.
  - "Ask before each session" holds every session for that phone until someone at the desk allows it.
  - The server re-reads them each second for running sessions: a phone that is no longer paired (unpaired from the CLI or the app, an expired guest grant), or whose Input, Sound or Microphone was turned off, loses its session within a second, whatever made the change.
  - Privacy mode belongs to the phone that turned it on: no other phone can refresh or end it, and it ends once that phone is no longer paired.
- **Abuse by a connection:**
  - A control packet is at most 4 MiB, on both control channels: a longer line ends the connection, before anything is buffered past that.
  - The control and stream ports hold at most 8 connections from one address and 128 in all; more are refused. The stream port counts an address only once it has answered a QUIC Retry, so a forged source address cannot use up a phone's share. The internet (WAN) listener holds at most 128 in all.
  - One phone runs at most two file transfers at a time, within the desktop's four.
  - A device id must be printable (no control or invisible formatting characters) and at most 128 bytes, on the control channel, the stream and the v2 handshake. A device's name is held to one printable line of at most 40 characters (`clean_device_name`): cleaned where it is kept, refused in the v2 handshake when it is not already so.
  - A folder listing fits in one packet: a huge folder is listed in part, and the phone says so.
  - Refusals are logged: the first on each connection at the default level.
- **Files:**
  - Transfers run inside TLS, pinned both ways: no other device can read the bytes, send them, or take them.
  - A paired phone moves files only once its key is bound (pairing binds it).
  - Received files are confined to one folder: Downloads, or the folder the owner chose (C2, desktop Settings "Received files land in"), never Pocketdesk's own state or config folders. They never overwrite anything, are size-limited, and are marked as downloaded on Windows. A phone with Files can fill whatever folder the owner chose, as it could Downloads.
  - Browsing and downloading are confined to the home folder. Hidden files, the server's own keys and settings, network paths and device names are refused, and links that lead out of home are refused too.

## Known limits

These are real gaps in the current design. Plan around them.

1. **Without the QR code, the first contact with an address is trust on first use.** Someone who can intercept that very first connection could relay the pairing. Scanning the QR code closes this.
2. **A phone paired before device keys, that has not streamed on the LAN since, holds no key yet.** Until it does, the control channel accepts it by its id alone, and it moves no files. The first LAN stream the desktop allows binds its key, and pairing it again binds it at once.
3. **Someone who knows an unpaired phone's id can get in the way of its pairing**, by asking for PINs or spending the wrong guesses under that id. They cannot pair as it without the PIN.

4. **The Mainline DHT links the desktop's WAN id to its home IP** (roadmap N3), unless `dht_publish = "off"` or `internet_path = false`.
   - The record is public to anyone who knows the id. By default it holds the relay URLs, which name your own relay when you run one. With `"addresses"` it also holds your home's public IP addresses.
   - In every mode, the DHT nodes that store the record see the home IP it was published from, hourly, so the id can be followed to the home over time.
   - A phone's WAN dial asks the DHT for the id, which shows strangers' nodes the phone's IP and the id it is looking for.
   - The id is in the pairing QR code, on each paired phone and on every relay the desktop uses. A forged record gets nowhere: it is signed, and the phone checks the desktop's key again when it connects.
5. **The connection limits are shared.** Phones behind one public address (carrier NAT, or a forwarded port) share that address's 8 connections, so one can use up the others'. Anyone who can reach the internet listener can hold its 128 until each handshake times out; the gate still refuses them.
6. **Privacy mode is held to its phone's id, as strongly as that id is held to a key** (limit 2). If that phone's Power permission is turned off, it cannot end the grab and no other phone may, so the local keyboard and mouse stay blocked until it expires (10 minutes).
7. **The desktop names itself to anyone who connects.** Any client that completes the TLS or QUIC handshake, with any certificate, gets the desktop's device id, name and plugin list before it is judged, and its certificate. Anyone on the network sees the same id and name in the mDNS announcement unless `lan_discovery = false`.
8. **The permissions limit what a phone may ask for, not what the desktop tells it.** A paired phone with every permission off still receives the desktop's notifications, its window titles (window list and workspace HUD), its battery, the wake details (the MAC) and the internet endpoint. Unpair a phone to stop them. The clipboard is the exception: the text you copy is pushed only to phones with Clipboard on, and with "Clipboard to phones" (`clipboard_push`) off, to none, though a phone in a session can still ask for it. A copy a password manager marks private (on Windows the formats that keep it out of clipboard history, counted private too when they cannot be read; on Wayland `x-kde-passwordManagerHint`) is never pushed, nor given to a phone that asks for the clipboard (since M3); an image copied here is told of too with "Images to phones' clipboards" on (M3, off by default), to phones only, which fetch it, but other copied secrets reach every connected phone with Clipboard on. The phone's "Computer's clipboard in the background" decides only whether the text is put on its clipboard: the phone receives it while its link is up either way.

9. **A phone with Links on can open web pages in this computer's browser** (roadmap T8a), up to 5 a minute, without asking, including pages on your home network such as a router's. Only `http` and `https` links go either way, never one to the computer's own loopback (`localhost`, 127/8, `::1`, in any spelling a browser reads as one) and never one with a user name or password. Links is on for every paired phone and guest by default, as Input is, and a phone with Input can type the same link. Turn Links off per phone in the Devices tab, or set "Links from phones" (`open_links = false`) to have links shown instead of opened. On the phone, any app can share a link to "Open on computer"; it goes to the last computer used.

10. **A phone with "My media on the computer" on tells the computer what it plays** (roadmap T8d): the title, artist and app, kept owner-only in the state folder while it is connected. The computer, with that phone's Media permission on, can pause and skip it. Both sides must agree: the phone's setting (off by default) and the desktop's Media switch.

11. **With "Names from my contacts" on, the phone tells its computer who texts it** (roadmap T8e): the sender's name from the phone's contacts goes with each forwarded text and is kept owner-only in `sms.json` (turning `sms_names` off forgets the kept names at the next start). A name says what the phone's contacts call that number; a text's sender number can be spoofed, so a name is not proof of who sent it.

12. **With "Let the computer answer notifications" on, the computer can act as you in the phone's apps** (roadmap T10c): it can press a notification's buttons (up to three, by title, never one Android runs only once the phone is unlocked) and reply to a chat, from the desktop app's Notifications page or, since N3, from the notification itself (a Windows toast's buttons and reply box; a Linux notification's actions and KDE's inline reply), at most 10 a minute. A toast can pop up under the cursor while you work, so one stray click presses whatever the phone's app offered ("Delete", "Archive"); desktop Settings "Answer in the notification" (`toast_answers`) turns that path off and leaves the Notifications page. Only a notification sent in full (not one whose content the lock screen hides, nor one carrying a code), and only from the phone's own computer. The notifications that can be answered are kept owner-only in `phone_notifications.json` while the server runs. It is off by default, and the desktop's Notifications switch for the phone turns it off too.

13. **The folders a phone shares (roadmap T10g) can be read by its computer.** In the desktop app's Phone tab, or by anything running as you that writes its requests, the computer lists them and copies any file in them, hidden ones (a leading dot) left out. Only folders the phone's owner picked in Settings, "Folders the computer may open", and only from that phone's own computer, with its Files permission on. Removing a folder there gives its grant back.

14. **With "New screenshots to the computer" on (roadmap T10h), every screenshot taken on the phone goes to its computer**, whatever it shows: onto the computer's clipboard and into its Downloads. On the computer it is then in the clipboard's history (Windows' Win+V, and its cloud clipboard if that is on) and in Downloads. Only to the phone's own computer, only images in a folder named `Screenshots` (an app that drops other images there sends them too), at most 10 minutes old; the computer's Clipboard and Files permissions gate each half. It is off by default.

15. **A phone's cast shows everything on its screen on the computer** (roadmap T10k), notifications and codes included, to whoever sees the computer's screen, while the phone's owner casts it. Android asks for consent each time, and its status bar shows that the screen is shared. The computer hands the picture from the server to the desktop app over loopback TCP, behind a token only its owner can read (`cast.json`); any program running as that owner can read the token, and so watch the cast. The Cast permission ("Show its screen or camera here", on by default) refuses it per phone; the same permission covers the phone's camera shown in that window (F6), which shows whatever the camera sees.

16. **The event log and hooks keep a record of what happens, and run what you tell them** (ecosystem phase 1a). `events.jsonl` in the state folder (owner-only, 1 MiB and one older file kept) lists sessions, phones linking, batteries, and the notifications, texts, files and links that arrive. By default it records only who, when and how much: the app a notification came from, a file's size, a link's host. With "details in events" on (`events_detail = "full"`) it also keeps their content (notification and text bodies, senders, file names, whole links), on disk, until the log rotates. A hook in `[hooks]` runs as you, with the event on stdin and in `POCKETDESK_EVENT`, through the shell: treat the event's fields as untrusted text (a phone chooses a notification's text and a file's name), and read the event from stdin: on Windows `%POCKETDESK_EVENT%` in a hook's command line is expanded before cmd parses it, so a phone-chosen field could run commands. A hook is stopped after 30 s, but programs it started in the background may go on. Turning "Event log" off writes nothing; hooks still run.

17. **A phone with the Tasks permission can run the commands you named as tasks** (ecosystem phase 1c), as you, through the shell: only those, by name, never a command of its choosing (that is Exec, off by default). "Ask first" is on for a new task, and holds each start for your Allow in the desktop app (a minute, then denied); turn it off only for a task that is harmless whenever it runs. Tasks is on by default for every paired phone and guest grant, like the other permissions but Exec, but nothing runs until you name a task. A run stops at its time limit (60 s unless you set another, at most an hour), though programs it starts in the background may go on. A phone may ask for 10 starts a minute, and a start that asks first holds one of the 2 places while it waits for you (up to a minute), so a paired phone can keep your other tasks waiting and keep asking.

18. **The browser extension can make this computer send a page, a link or an image to your phone** (ecosystem phase 1d), when you right-click one: the browser starts `pocketdesk browser-host` as you, and only the Pocketdesk extension's id may talk to it. For an image, Pocketdesk downloads the address itself (`http`/`https`, never the computer's own `localhost`, the address and each of at most 5 redirects alike, though a name that resolves to an address on your network is not refused; at most 32 MB, only a PNG, JPEG, GIF, WebP, AVIF or BMP by its content type, and named for that type: an address ending `.apk` arrives as a `.png`; SVG is not sent), so the site sees this computer fetch it, not the browser. The phone's Links and Files permissions apply. Another extension cannot reach the host, but anything running as you could run it, as it could any of your programs.

19. **Home Assistant sees your computer and phones, and can start your tasks** (ecosystem phase 1e), when you turn it on and name an MQTT broker. The server publishes, retained: whether it runs, the number of sessions, whether a phone's screen is shown, each paired phone's battery and connection, and your tasks' names (never their commands). Not retained, as they happen: each event's kind and phone, so the broker learns that a notification, a text, a file or a link arrived and from which phone (by the first 8 characters of its id), never what it said or was called. The connection is plain MQTT, so anyone on the network path can read it and the password, and anyone the broker lets publish to `pocketdesk/<computer>/task/…/run` can press a task's button: a task that asks first still waits for your Allow at the desk, but one that does not ask runs. Give the broker a password, keep it on your own network, and leave "ask first" on for any task you would not let your broker start. The password sits in config.toml, which Pocketdesk writes readable only by you; a config.toml you wrote by hand keeps the permissions you gave it until Settings saves it. Turning the bridge off marks the entities unavailable in Home Assistant; delete the device there to remove them.

20. **With "Tell other apps what happens" on, any app on the phone learns when you use Pocketdesk** (ecosystem phase 1f): the broadcasts name no app, since an automation app cannot hold a permission of ours, so any app may hear when a session starts and ends, a file or link arrives, files finish sending or a task ends, with the computer's saved address, a file's type and size, and a task's name and exit code. Never a file's name, a link, a task's output or a notification. Any app can also send the same broadcasts, so an automation should not treat one as proof that it happened. Off by default.

21. **Another of your computers, once paired, may do what a phone with Clipboard, Files and Links may** (ecosystem 2f, 2g): browse and fetch files under your home folder, send links that open in your browser, and, with "Clipboard with my computers" on on both, share the clipboard both ways (text, and with no text an image, which rides the link's file streams and so only with "Files over the internet" on; a password manager's private copies stay where they are). It may not send input (unless you give it Keyboard and mouse, limit 59, which also lets it hear this computer while its pointer is here, limit 61, or "Control the mouse and keyboard" for its screen window, limit 62, or it paired both ways, limit 64), sound, power or commands, and a screen session from it (limit 62) is held for you to allow, unless the two computers are paired both ways (limit 64), when nothing is held. Pairing it takes your PIN, inside the pairing link that the Pair tab copies, so treat that link as the PIN: Pocketdesk never sends a pairing link from the clipboard to a phone or a computer, but it stays on this computer's clipboard (and in Windows' clipboard history) until you copy something else; its certificate is pinned from the link before the PIN is sent. Unpairing on one computer does not unpair it on the other: unpair it in the other's Devices page too. The link between them rides the internet path (iroh), so relays and the DHT see what they see for a phone (the start of this page, and limit 4). A computer running a Pocketdesk from before this pairs the other as a phone, with a phone's default permissions: update both first.

22. **KDE Connect devices can find this computer and connect to it, on by default** (ecosystem 3a; desktop Settings "KDE Connect devices" turns it off). The desktop app's "Find KDE Connect devices" broadcasts this computer's name and a KDE id of its own on the local network; a device that hears it (or knows the address) dials the control port. That path takes TLS 1.2 as well as 1.3, since KDE Connect Android caps at 1.2, and holds a device to the id its certificate names; the Pocketdesk road stays TLS 1.3 only. A device that has not paired is given nothing (at most 4 such links from one address, closed after 5 silent minutes, one pairing request at a time each). Pairing (3b) is held for you with a code both screens show, either way: a device's request waits for your Allow, and a device's acceptance of yours waits for your Confirm. **The code is the only check**: any device on the network can ask, under any name, and can claim a device's id while that device is not connected, so compare the code on both screens before you answer, and do not answer a request you did not expect. Your answer names the code you saw, so it is not taken for a request made since. Once paired, a device reconnects only with the certificate it paired with, and may do only what its own switches allow (3c), narrower than a phone's: ping; its battery; the clipboard both ways (your copies go to it while "Clipboard to phones" is on); being rung from here; and, only when you turn it on, sending files into Downloads (fetched from the device's own address, held to its paired certificate, marked as downloaded); and its notifications (N9, on by default, sent only with notification sync on in its own KDE Connect app), **shown here in full**: unlike Pocketdesk's phone app, which keeps lock-screen-private content and one-time codes off the computer, KDE Connect sends what it sends and this computer cannot tell what is private, so the text reaches the toast, the notification centre and, with "details in events", the event log and hooks; turn the device's "Show its notifications here" off, or choose apps in its KDE Connect app. Nothing else it sends is taken, Pocketdesk's own packets among them. A file stops on the way if you unpair the device or turn Files off, and a device sends at most 4 at once.

23. **Your computer can ring a paired phone loudly** (N1): its Ring button or `pocketdesk ring` make the phone ring for 30 s at its alarm stream's full volume (at the owner's alarm volume on Android 17 and newer, where an app may not raise it from the background), through Do Not Disturb when alarms may sound. Only a paired phone with its Ring permission on (Devices) and its own "Ring from the computer" on, or a session or the remote open, rings; at most once a minute, and never another computer. Anyone who can use the owner's account on the computer can therefore ring the phone.
24. **With "Remember the screen-sharing grant" on, sessions start with no one at the computer** (N8; GNOME and KDE, off by default): the portal's grant to share the screen (and, where input goes through the portal, to drive the keyboard and pointer) is kept until revoked, with its restore token owner-only in the state folder (`portal_restore_token`, `portal_remote_token`). Anyone who can read your state folder can start a screen share as you, without asking; every session is still held to a paired phone, its key and its permissions, and "ask first" where set. Revoke it in the desktop's own privacy settings (GNOME: Privacy, Screen Sharing; KDE: the portal's permissions). Forget the grant in the app, or turning the setting off, only drops the local token, so the next session asks again; the desktop's own permission stays until revoked there.
25. **With the phone's "Let the computer control this phone" on, the computer it shows its screen to can act on it** (C8; off by default, and it needs an Accessibility service the owner turns on in Android's settings).
    - **What it can do:** only during a cast, and only from the computer the phone itself opened the cast to, that computer can tap, drag, scroll, type into the focused field, and press Back, Home, Recents and the shade. Nothing is touched or typed while the phone is locked, so the computer cannot enter its PIN or pattern; Back and Home still go.
    - **On the computer:** any process running as the owner that can read the cast's token (`cast.json`, owner-only) can send control. The desktop app's "Control phones from their screen window" is the app's own choice, not a gate the server enforces. The phone's setting is the real gate.
    - **What Android allows:** the service may read the screen. Pocketdesk reads only the field it types into and sends nothing it reads.
    - **Advanced Protection:** Android 17's Advanced Protection does not allow the service.

26. **With the phone's "Recent photos on the computer" on, its computer can see its newest camera photos** (C7; off by default, and it needs photo access). The computer asks; the phone answers its own computer only, with thumbnails of at most 24 photos in DCIM, and sends a full photo only when asked, through the usual transfer. The thumbnails are kept owner-only in the computer's state folder, so anyone who can read that folder, or use the owner's account on the computer, can see them; turning the switch off on the phone stops further answers, and they are dropped when the server starts again.
27. **With the phone's "Let the computer mute this phone" on, its computer can turn on its Do Not Disturb** (D2; off by default). The computer asks with a number of minutes, at most a day; the phone takes it only from its own computer, only when it is not already quiet, and ends it at its time unless the owner changed it meanwhile. Meanwhile calls and messages the owner's own Do Not Disturb settings let through still come, but others are silenced: anyone who can use the owner's account on the computer, with the phone's Mute permission on (Devices), can quiet the phone for up to a day at a time. The phone also tells that computer whether it is in Do Not Disturb, which says something about the owner's day.
28. **With "Clipboard history" above 0, the computer keeps in plain text what crossed** (D3; off by default). The last texts that went between this computer and its phones, either way, sit in `clip_history.json` in the state folder, owner-only, until they fall off the end, the history is cleared, or it is turned off. A copy a password manager marks private never crosses and so is never there, but a secret copied without that mark, or one the phone's tile sent after you confirmed it, is; so is a KDE Connect device's text. Anyone who can read your state folder, or use your account on the computer, can read them. A pairing link, anywhere in a copy, is never kept.
29. **With "Let the computer answer notifications" on, a chat's recent messages reach the computer** (D4). For a chat notification sent in full, its newest ten messages, other people's names and texts included, go to the computer, where they are kept owner-only with the notification (`phone_notifications.json`, the newest 30). A thread in which any message looks like a one-time code is not sent. Anyone who can read your state folder, or use your account on the computer, can read them; turn answering off in the phone's Settings to keep them on the phone.
30. **With "The phone's folders as a drive" on, any program on the computer that has the drive's address can read the folders the phones share** (D8; off by default). The server serves them read-only as WebDAV on loopback only, at an address with a random token in it, kept owner-only in `drive.json` and new each time the drive starts. Anyone who can read your state folder, or run programs as you, can find the address and read every folder a phone shares while it is connected, as the Phone page can. Files fetched through it wait in `drive_cache/`, owner-only, until served.
31. **"Lock this computer when it leaves" is a convenience, not a boundary** (D9; off by default; Windows, and Linux under GNOME, KDE on X11 or X11, R3). The computer locks when the phone's link has been gone for a while and nobody has used the keyboard or mouse, so a phone that keeps its link from across the house, or that someone else keeps near the computer, keeps it unlocked; and a link can drop for other reasons (the phone asleep, Wi-Fi), so it may lock while you read. A lock that fails is tried again a minute later. Lock the computer yourself when it matters.
32. **A deck button does its action as the phone pressing it may** (F1). The buttons are yours, set up in the desktop app's Settings, and a phone sees only their labels; but a phone with "Control the mouse and keyboard" can press a button's keys or type its text on the computer without a session, as its mouse and keyboard packets already can, a task button starts the task as a phone's start does (asking first when the task asks), and a link button opens its link. Leave out of the deck what a phone should not set off; turn "Deck" off in Settings to refuse every press.
33. **A paired phone may see how this computer is doing** (F2; on by default): the CPU and memory in use, each fixed disk by its drive letter or mount point (a Linux mount point can hold your user name), the battery and uptime. Turn "This computer's state" off in desktop Settings to answer none of it.
34. **With "Ringing calls on the computer" on, the caller reaches the computer** (F5; off by default): the number, and the contact's name with "Names from my contacts", as the phone's own notification, whatever the phone's lock-screen privacy or its notifications switch say; and the computer may then silence the ring or, with "Let the computer decline calls", end the call.
35. **With the phone's "Pictures in notifications" on, a notification's picture reaches the computer** (K3; off by default): a photo someone sent in a chat, or a contact's photo, for a notification the phone sends in full, kept owner-only in the state folder while the notification shows here. Anyone who can read your state folder, or use your account on the computer, can see it meanwhile. Apps' icons always go and are kept by app; turn "Apps' icons and pictures" off in desktop Settings to keep neither.
36. **This computer can clear the phone's notifications** (L1; on by default on both sides): a notification the phone sent it, closed here or cleared on the Notifications page, is cleared on the phone, at most 30 a minute, never a call. Anyone who can use your account on the computer can clear what the phone sent it. Turn "Let the computer clear my notifications" off on the phone, or "Clearing here clears it on the phone" off here.
37. **With the phone's "Calls from the computer" on, its computer can open the phone's dialer with a number** (L4; off by default): a number only, never a code (`*` and `#` are refused), and never a call, which needs the owner's tap on the phone. Anyone who can use your account on the computer can put a number in front of you there, ten a minute at most.
38. **With the phone's "Commands from the computer to my automation apps" on, its computer can trigger the phone's automations** (L6; off by default): a name and a text, to Tasker, Automate or MacroDroid as Settings names, never to another app. Anyone who can use your account on the computer can send them, 30 a minute. And any app on the phone can send the same broadcast to that automation app, which cannot tell it from Pocketdesk's: an automation it starts should not do what a stranger's app must not.

39. **With "Other computers of mine" on for a computer, it sees the phone's notifications too, and may answer and clear them** (L8; off for each computer): what the phone's own computer gets (titles, texts, contact names, pictures when those are on). While answering is on, or clearing within ten minutes of a notification, the phone keeps a link to each computer picked (at most three, on this network or the tailnet, TLS to the computer's pinned key), and those copies keep their buttons, reply and thread: that computer may answer and clear them as the phone's own computer can, ringing calls included (Silence, and Decline where allowed), under the phone's same switches and budgets, which all its computers share. Without a link a copy goes as a one-off connection, without what offers an answer. Texts are not copied. The phone names such a link as for copies only, so that computer neither pushes to it nor counts the phone as linked.
40. **A paired phone may ask what this computer allows it** (M2a): for each of its features, whether its own permission allows it and whether this computer's Settings let any phone have it, booleans only, about itself only. **Someone else's phone, and every guest, sends files and links only** (M2b): it may not browse this computer's files (Browse, its own permission since M2b) or drive it, and its sessions are held for the owner; but a session the owner allows still shows the screen, as for any phone. The Pair page's choice rides the PIN file; an older server that reads a new PIN file ignores the choice and pairs the phone as the owner's.
41. **A photo's place goes with it when the phone's switch says so** (M5): with "Photos keep where they were taken" on (off by default), a photo the phone sends to its computer keeps its GPS tags, which say where it was taken, and so where someone was. Only in a photo the person sent, or one the computer was allowed to fetch (recent photos, screenshots, the drive); a photo the phone could not open whole goes without its place, as before.
[docs/protocol.md](docs/protocol.md) lists every port, packet, file and outside party, and what each one sees.
42. **The computer can type on the phone without seeing it** (M4): with the phone's "Typing from the computer's keyboard" on (off by default), its own computer can type into the field in front and press Back, Home and Recents, with no picture of the screen, so it cannot see where the text lands. The phone refuses password fields and a locked phone, types only while its notification (with Stop) can be shown, and drops typing more than 10 seconds old; the computer needs its Settings "Control phones from their screen window" and the phone's "Show its screen or camera here".
43. **A web page can start a dial** (M8): with "Open phone numbers on the phone" on (off by default), a `tel:` or `callto:` link a page offers, once clicked, opens the phone's dialer with its number. The owner still presses Call there, and codes (`*`, `#`), extensions and parameters are refused, as L4's numbers are.
44. **Home Assistant can start a phone's automations** (M9): each of Settings' "Phone commands" is a button in Home Assistant, so anyone who can press its buttons, or publish to its command topic on the broker, can hand that command and its text to the phone's Tasker, Automate or MacroDroid, at most 30 times a minute for a phone, and only while the phone's own "Commands from the computer to my automation apps" is on. The broker sees the labels, never the names or texts.
45. **The phone reads each copy by itself** (M10): with "Send my copies by themselves" on (off by default), the "Pocketdesk control" Accessibility service watches the system's windows for the clipboard preview, keeping a hash of what the preview shows, and then a window that never shows reads the clipboard and sends the text to the phone's own computer. A copy an app marks sensitive is never sent, but an app that does not mark its secrets has them sent. Android shows "Pocketdesk pasted from your clipboard" each time.
46. **The phone tells its computer what it plays without a session** (N2): with "My media on the computer in the background" on (off by default), the notification listener sends the title, artist, app and cover of what any app plays to the phone's own computer while it is linked, again each minute while it plays, so listening history leaves the phone in the background. The computer keeps the newest report and its cover owner-only, and forgets both when the phone stops playing, unlinks or loses its Media permission, and at each start. The cover is checked by its header and size before anything decodes it.
47. **The computer can open a phone notification's app on the phone** (N3): with "Let the computer open my notifications" on (off by default), the phone's own computer can make it run a notification's tap action, which shows that app on the phone's screen, as a tap on it would. Only a notification the phone sent it offering this, still shown, while the phone is unlocked and awake, at most 10 a minute with answers. With Pocketdesk control on, the app starts from the background (Android 14's opt-in, which the Accessibility service allows); without, the phone shows a notification to tap. What the app shows is on the phone, not the computer.
48. **A phone's ongoing updates go to the computer while they last** (N4): with "Ongoing updates on the computer" on (off by default), a shared app's progress bar or timer and its words go to the phone's own computer at each step, at most every 5 seconds, for as long as the notification stays, and a navigation or delivery app's say where the phone is. The computer keeps the current cards owner-only in `phone_live.json`, emptied at each start, and drops a card with its notification's end. A redacted notification's bar is not sent.
49. **The computer's music shows on the phone's lock screen** (N5): with "Computer's music in my media controls" on (off by default), the phone asks its own computer, which then sends the title, artist, app and cover of what plays there each time it changes and again each minute, while the phone is linked and keeps its Audio permission. The phone shows them in a media notification visible on its lock screen and on a paired watch, and Play/Pause, Next and Previous there, or a headset's buttons while it is the session playing, reach the computer's player without unlocking the phone. The cover is whatever the computer's player (or a web page playing in a browser) gives as artwork: the computer checks it is a JPEG or PNG of at most 256 KiB, and the phone decodes it at most 1024 px a side. Pocketdesk's own entry in the computer's media controls (the phone's music, K7) is never sent back, and the phone never reports its own session as the phone's music.
50. **Any program on the computer that has the drive's address can add files and folders to a phone's folder its owner marked** (N6): with "The phone's folders as a drive" on and the phone's "The computer may add files" on for that folder (off by default), a file copied onto the drive is taken into an owner-only folder on the computer and fetched by the phone, as any file sent to it. Only marked folders take anything, names starting with a dot are refused, and nothing on the phone is replaced, removed or renamed; desktop Settings "The phone's folders take files" turns it off on the computer. Locks the drive answers so Windows writes hold nothing.
51. **A phone learns whether each of the owner's computers is in use** (N7): a computer answers any paired phone with the Notifications permission that asks, whatever that phone's own switch says, whether its keyboard or mouse was used in the last two minutes; desktop Settings "Tell phones when this computer is in use" is on by default, and off it answers nothing (as it does while paused, with phones' notifications off, or on Linux). Pocketdesk's phone asks only with "Toast only on the computer I'm using" on (off by default), every 15 seconds in the ten minutes after a notification; no times, apps or windows are said, though a phone asking often can tell within its asks when the two minutes ran out. A computer in use with an app muted (K2b) still counts as in use, so the others hold that app's notifications too, and no one sees them pop up.
52. **Any app on the phone can start the computer's tasks and press its deck buttons by name** (O1): with the phone's Settings "Let other apps run the computer's tasks" on (off by default), Pocketdesk takes `RUN_TASK` and `PRESS_DECK` from whatever app sends them, since Android lets no automation app hold a permission of Pocketdesk's. They reach only a saved computer, at most 10 a minute from all apps, and the computer's own rules still hold (the phone's "Start my tasks" and Input permissions, and a task that asks first asks at the desk), so they can do no more than the phone's own Tasks sheet and deck. Their outcomes are told as events any app can read, with the task's name or the button's label; with the switch on, an app can also tell from them which computers are saved and which task names and button labels exist, which the phone's own sheets otherwise keep to themselves.
53. **The phone's own computer can take a screenshot of the phone and lock it** (O2): with the phone's "Let the computer take screenshots and lock this phone" on (off by default) and its Pocketdesk control service, the computer it works with may ask, 10 times a minute, and the phone does it without a word on its screen. A screenshot is never taken of the lock screen, and reaches the computer only through "Send new screenshots" (T10h), so what the phone shows when asked lands there; the computer's per-phone "Take screenshots of it, lock it and open its apps from here" permission (on) turns it off from that side.
54. **A host on the network that forwards to a paired computer can move its card to the host's address** (O3): when a saved computer announces itself at a new private address, the phone follows its card there once the computer answering proves the key the old address was pinned to, and the old address no longer answers as it. A host that relays the connection to the real computer passes that proof, so it can take the card while the computer's old address is down. What crosses stays end to end with the pinned computer, which the relay cannot read or change, but it can then withhold the connection; the card returns once the computer is found again at an address that proves itself. Cards saved by name, or by an address still reached, never move.
55. **The phone's own computer can list the phone's apps and open one** (P2): with the phone's "Let the computer open my apps" on (off by default), the computer it works with may ask for the names of the apps in its launcher (never Pocketdesk itself) while the phone is unlocked, and keeps them owner-only (`phone_apps.json`); it may then ask to open one of the apps listed, 10 times a minute, never on a locked phone. With the Pocketdesk control service bound it opens at once (Android's background-start opt-in); without it the phone offers "Tap to open" for ten minutes. The computer's per-phone "Take screenshots of it, lock it and open its apps from here" permission (O2's Phone actions) holds both.
56. **A rule of "Links by site" hands a phone's link to a program of the owner's choosing** (P8): desktop Settings may name a program for a site, which then runs with the link a paired phone with Links on sent as its one argument, never through a shell, at most 8 at once. The link has passed the same checks as any (http or https, a host that is not this computer, no credentials); a program is named by its whole path, never a batch file. A rule `show` keeps a site's links from opening at all.
57. **A permission profile is read when a phone pairs with it** (P9): a Pair-page code that names a profile pairs the phone as someone else's (its key bound as a guest's, never another phone's proved id) with the profile's permissions as they are then, not as they were when the code was shown; the Pair page says what it allows, and a profile saved again says it replaced one. A phone paired already keeps only what both allow. A profile may hold any permission the owner saved in it, commands among them.
58. **The phone's own computer can ask for its contacts** (P10): with the phone's "My contacts on the computer" on (off by default) and Android's contacts permission, its own computer may ask, 10 times a minute, for every contact's name and numbers (nothing else of them), under the phone's Texts permission here. The computer keeps them owner-only in its state folder and forgets them when Texts is turned off or the phone unpaired (at once in the desktop app, else at the server's next start); the phone's switch turned off stops new lists, not the one kept.
59. **A paired computer with "Keyboard and mouse" can type and click here** (the shared keyboard and mouse): once its cursor comes onto this computer's screens, whatever it sends is typed, clicked and moved here as if from this computer's own keyboard and mouse, into whatever is in front, on Linux a lock screen included (Windows keeps its sign-in screen out of reach of injected input). Both must hold: "Share my keyboard and mouse with my computers" (`shared_input`) on here, and that computer's "Keyboard and mouse" permission on in the Devices page; both are off until you turn them on, a phone never drives this computer by it (only one of your paired computers does, whatever a permission profile says; for a phone the same permission means the other way, limit 60), and turning either off stops it after about a second and lets go of what it held down. What it pressed is let go of when its cursor leaves, when it asks, and when its link goes; a computer that has sent nothing for a second (it sends a note several times a second while it drives) is taken to have gone. It rides the link between the two computers only when that link is direct, not through a relay; this computer looks for itself, refusing a cursor that arrives over a relay and letting go of one whose link turns relayed. While sharing is on, activity on any of your computers allowed to drive this one keeps this one from idling (its screensaver held off on Linux, the display kept on on Windows) for 10 s after the last sign of someone there, whether or not its cursor is here. What it says of its screens is kept owner-only in `shared_screens.json`. The other way, from Windows (or Linux, limit 63) with "This computer's keyboard and mouse can move to the others" (`shared_input_drive`) on as well: once the pointer leaves for another computer, everything typed and clicked here (a password included) goes to that computer and none of it to this one, until the pointer comes back, the switch key is pressed, Windows locks, or that computer stops answering for a second (asked five times a second; the pointer crosses onto it again once it answers); Ctrl+Alt+Del stays with this computer, and its lock brings the keyboard and mouse home; Win+L while the pointer is away is never sent on: it brings the keyboard and mouse home and then locks this computer. With "Clipboard follows the mouse" (`shared_input_clipboard`, on by default), what is copied here goes to the computer the cursor goes to, and what was copied there comes back as the cursor comes home, at each switch, even with "Clipboard with my computers" off: the text, or with no text the image (a PNG of up to 32 MB, on the link's transfer streams as files go, so only with "Files over the internet" on), never a password manager's private copy, a copy from a program Settings keep here, or a pairing link. A computer takes it only with sharing and that setting on there, and only from a computer it shares the keyboard and mouse with (one it lets drive it, or one that answered its hello on the link up now); but such a computer can set this computer's clipboard, text or image, that way at any time, not only at a switch: the computer taking it cannot tell a switch from any other moment. The other way, such a computer can fetch only the image this one told it of at its last switch, and only until the next. With "Drag files across the edge" (`shared_input_files`, on by default), files dragged in Explorer and let go while the pointer is on another computer are sent to that computer, as the desktop app's Send sends them: only the paths Windows hands over with the drop, nothing read beyond them, and only with "Files over the internet" on here and Files allowed for this computer there.
60. **Your computer's keyboard and mouse can touch and type on your phone** (BK5, the phone as a screen): with the phone's "Let my computer's keyboard and mouse use this phone" on (off by default) and C8's Accessibility service on there, and that phone's "Keyboard and mouse" permission on in this computer's Devices page (off by default, and never set by a permission profile), the phone's own computer may carry its keyboard and mouse onto the phone when its pointer crosses the phone's edge on the Keyboard and mouse page, from Windows with sharing and driving on. Then a click there taps, a drag swipes, the wheel scrolls, the right button is Back, the middle Home, and keys type into the field in front, on a US keyboard (never with Ctrl, Alt or a Windows key held), as if the owner did them on the phone, in any app; everything typed and clicked on the computer meanwhile goes to the phone, a password included. The phone takes it only from its own computer, never on a locked phone (Back and Home aside) and never into a password field; it shows its own pointer while it does. Every finger down is lifted when the pointer leaves the phone, when either switch turns off, when the link goes, and when the computer sends nothing for a second; the computer brings its keyboard and mouse home when the phone stops answering its pings for a second. It rides the phone's own link, at home or through the internet path. What the phone says of its screen (its size and rotation) is kept owner-only in `shared_screens.json`. The hidden `pocketdesk phone-screen-test` (a tool for checking this without moving the computer's mouse) lets any program of the owner's account on the computer send a ready phone the same input, from the server, while sharing (`shared_input`) is on there, with no mouse crossing; as `share-test` does for computers.

61. **A computer that may drive this one can hear it** (BK6, sound follows the mouse): a computer allowed to drive this one ("Keyboard and mouse" on here for it, with `shared_input` on) can, while its cursor is on this computer's screens, ask for this computer's sound, and gets whatever plays on its default output (a call, a video, a notification's chime) for as long as its cursor stays, at 96 kbit/s on their direct link, never over a relay. There is no setting for it on this computer: whoever may drive this computer may hear it, as they could in front of it. Nothing is captured while no such computer asks, and the capture stops when its cursor leaves, it stops asking, it goes silent for a second, or its link or permission goes. The setting to hear (`shared_input_sound`, off by default) is on the driving computer, and it plays only the sound of the computer it asked.
62. **A paired computer can show this computer's screen in a window, and with Control on, use it** (BK7): one of your computers paired with this one can open a session here as a phone does, from "Show its screen" in its Settings, under Other computers, by the home network or the internet path, to show everything on this screen there, to whoever sees that computer's screen. It is judged as any paired device: held to its keys, with its permissions, and by default (a computer's "Ask before each session") only once someone at this computer allows the session; turn that off only for a computer you trust to look while nobody is here. Its "Control the mouse and keyboard" here is off by default: off, the session is view-only and this computer injects nothing it sends; on, that computer's window clicks and types here as a phone in a session does. Its sound comes only with "Hear and change this computer's sound" on for it (off by default). On the computer that shows it, the server hands the picture to its desktop app over loopback TCP behind a token in `view.json`, owner-only: any program running as that owner can read the token, watch the screen and, while Control is on, send it input through the relay, which passes on only pointer, key and text packets, and say the window's focus (PC3, limit 65), which moves the clipboard between the two computers, either way. The session shows in this computer's session list by that computer's name, and End ends it.
63. **On Linux, the desktop's input-capture permission lets Pocketdesk take this computer's keyboard and mouse** (BK8, Linux drives too): with sharing and "This computer's keyboard and mouse can move to the others" on, the server asks the desktop's input-capture portal (GNOME 45 or later, KDE Plasma 6.1 or later, Hyprland with xdg-desktop-portal-hyprland 1.4 or later) for the keyboard and the pointer, and the desktop shows its own dialog once. What that grants: the desktop watches this computer's screen edges that lead to another computer, and when the pointer is pushed past one of them, every key and click from then on goes to Pocketdesk (and on to the computer the pointer went to), a password included, none of it to this computer, until the pointer comes back, the switch key is pressed, that computer stops answering for a second, or the desktop takes them back (as it does for its lock screen); at home Pocketdesk sees no key at all, only that an edge was pushed. The portal's answer comes back as a restore token, kept so the dialog does not ask again at every start: owner-only in the state folder (`input_capture.token`, replaced at each start, never logged), and anyone who can read it as the owner could start such a session without the dialog. Delete it, or revoke the permission in the desktop's settings where it offers that, to be asked again.
64. **Pairing both ways gives each computer full, unattended view and control of the other** (PC1, both are mine), and pasting such a link gives **the computer that made it** that control of **the computer you paste it on**. It takes a yes on both computers. On the one whose Pair page makes the link, "This is another of my computers (let it see and control this one without asking)" ticked beside it (off by default; only with your own code, never a guest's, someone else's or a profile's; unticked again after that code). On the one you paste it on, Settings, Other computers names the link's computer and says it would "see and control this computer at any time without asking", with the addresses the link names, and pairs both ways only if you tick that it is your own computer and the link names that computer's internet endpoint; unticked (or with no endpoint, which the page says), it pairs one way and trusts the link's maker with nothing. Granted, each computer trusts the other with a computer's permissions plus "Control the mouse and keyboard" and "Keyboard and mouse", and no session asked first: whenever it likes, with nobody at this computer, the other can show this screen (limit 62) and click and type here, through its window or the shared keyboard and mouse (limits 59 and 61). **The risk on the pasting side:** a pairing link is not signed, and anyone can make one or edit one on its way to you (in a chat, an email, a synced note). A link that asks for both ways, ticked and pasted, hands this computer to whoever made the link, whatever name it shows: the name is the link's own word, so check the addresses shown under it are your computer's. Tick it only for a link you copied yourself from your own computer's Pair page, moments before. The pasting computer trusts the other the moment it pairs. Any program running as you can leave the same request the desktop app leaves, ticked (its folder is owner-only, as `view.json` is for limit 62), so a program running as you could pair this computer both ways with a link of its choosing. A link that reuses the id of a computer listed here with another certificate is refused, so a link cannot quietly take the place of one of your computers; unpair that computer first if it really was reinstalled. **The risk on the making side:** the link and its PIN are the keys to this computer for the 5 minutes the code lives, so paste it only on your own computer and copy something else after (Pocketdesk sends a pairing link to no phone or computer, but it stays on the clipboard). This computer grants it only when its own PIN file says the code was minted with the box ticked, so `mine=1` added to an ordinary link, or taken off, gives an ordinary one-way pairing; the PIN is single-use and discarded after 5 wrong guesses, and the computer pasting the link has already pinned this one's certificate from it. Anyone holding one of this computer's codes who pairs under the id of a computer listed here, with another certificate, is refused before anything of that computer is touched, whether it pairs as a computer or as a phone. That includes a listed computer pairing again under its own id over the internet road, where it proves no certificate: unpair it first, or pair it again at home. The making side's grant waits until the other computer has recorded the pairing: until then the other is trusted as a computer paired one way ("Mine once linked" under Other computers). It is shown by this computer's dial to the other being admitted there (only a computer it trusts is), or by the other saying so on the link it opens after pairing, a connection over the internet road that proves the iroh key it named as it paired where it says so, which it does only once it has recorded the pairing (its pairing connection does not count). With no such link within ten minutes of pairing, the grant lapses: the other stays paired one way here, and Other computers says so ("Paired one way here: no link came from it within ten minutes; pair again for both ways"). On the other computer it stays as you paired it there, still trusting this one with control: unpair it there too. It is dialed over the internet only at the iroh key it named as it paired. Revoke it at any time: turn "Ask before each session" on and the Control switches off on its Devices page, or Unpair it there or under Other computers, which takes both directions away on that computer; the other computer is not told, so unpair it there too. Pairing again without the box changes each side differently: the computer whose link it was keeps the other trusted as a computer paired one way (a computer's narrow permissions, its sessions asked first), and the computer that pasted lists the other one way and no longer trusts it at all.
65. **The clipboard crosses as a computer's screen window gains and loses the focus** (PC3, `computer_view_clipboard`, on by default on both computers). While the window on computer A controls computer B (B's "Control the mouse and keyboard" on for A), A pushes its clipboard to B each time the window gets the focus, and B pushes its clipboard back to A each time the window loses it or closes: whatever was copied last on either side, including something copied long before and forgotten, a text up to 256 KB or with no text an image of up to 32 MB (images only with "Files over the internet" on). What stays: a password manager's private copy (as limit 8 describes), a copy from a program Settings keep here ("Never send copies from", Windows) or that looks like a pattern kept here ("… that look like"), a pairing link, and anything that came from the other computer itself. B takes such a push only from a paired computer whose screen session on B takes its input now and that has the Clipboard permission on B, and answers the ask only to such a computer, whichever road the packet comes by; A takes B's answer only within 15 s of asking, once, and only from the computer it asked. **B cannot tell that the window's focus really moved: the ask and the mark are A's word.** So while A controls B's screen, A can read B's clipboard whenever it changes, not only as its window loses the focus: B answers at most once every 2 s per computer, and only with a copy new since its last answer to that computer. The same way, A can set B's clipboard at any moment while its session runs. Turn Clipboard off for A on B's Devices page (or this setting off on B) to stop both. Turn the setting off on either computer to stop it there; "Clipboard with my computers" (limit 21), when on, already shares every copy and the window then sends nothing of its own. Files dropped on the window go as any file sent to that computer (limit 21): only with Files on for A on B and "Files over the internet" on both, into B's Downloads.
66. **A nearby computer can ask to pair, and the code is only as good as the look at it.** Any computer on the network can send this one an ask (docs/protocol.md §2.7); it grants nothing until both owners say yes: the owner here presses Accept, and the asking computer's owner confirms that its screen shows the same code (as each side does in Bluetooth's numeric comparison). The asking computer pairs only once its own owner confirmed, so a computer in the middle that answers "accepted" at once pairs nothing there, and the PIN the asker then gets pairs only the certificate whose code was matched, once, within two minutes, and only as a computer, with a computer's narrow permissions; a pairing with it that asks as a phone is refused. The asking computer pins the other's certificate only at the address it dialled and saw it at, and no pairing re-pins an address another listed computer is at. A nearby ask, and the pairing its PIN makes (checked again then), never takes an id already in use here: one paired here as a phone or a computer, one this computer paired with, or one bound to another key. One ask is shown at a time (another asker hears "busy", which tells it that an ask is on screen), one address may ask at most three times a minute, and at most three asks are shown in ten minutes from all addresses together. An ask that fails before it is shown (a wrong reveal, or one that leaves or stays silent after this computer's nonce) counts host-wide: after three in ten minutes, no ask is taken from anyone until the ten minutes have passed. The same pause follows three asks shown in ten minutes. The Pair page notes each failed ask ("A nearby pairing ask failed (a wrong code or a dropped connection)"). One notification is shown per pause, and while it lasts the Pair page says until when, and that "Let computers nearby ask to pair" turns asks off. Anyone on the network can keep nearby asks paused this way; it fails closed, and a pairing link still works. An ask whose connection closes frees the screen at once. "Let computers nearby ask to pair" (`nearby_pairing`) turns asks off. The code is six digits from both certificates and both computers' nonces (the asker commits to its own first), so a computer in the middle shows a different code on each side unless it is lucky. It can check its luck at this computer's nonce before revealing. A miss it leaves is a failed ask, and one it reveals anyway shows the owner a prompt with a code the other screen does not show. Both are capped host-wide, at three failed asks and three prompts in ten minutes. That is at most six tries in ten minutes, each one in a million, and each one seen by the owner (a notification or a prompt); an owner who accepts without comparing the two screens accepts whoever asked. The asker learns no more before Accept than the announcement and the control channel's opening already say (limit 7): a nonce, or "busy" or "unavailable" (asks off, too many, or paused alike). Nothing new is announced: the ask rides the existing announcement and pairing packet. "Both are mine" still needs both owners' tick (limit 64).
67. **On Windows, a computer's screen window in full screen takes the Windows key and Alt+Tab from this computer** (PC4, `computer_view_grab_keys`, on by default). While the window controls the other computer, has the focus and fills the screen, the desktop app puts a low-level keyboard hook (`WH_KEYBOARD_LL`) in for this session: it sees every key pressed on this computer while it is in, and keeps the Windows key (with every key pressed while that is held), Alt+Tab, Alt+Esc and Ctrl+Esc from Windows, sending them to the other computer through the window, as the window already sends what is typed in it. Every other key it passes on untouched, it never writes a key anywhere, and it ignores keys other programs inject. It comes out when the window loses the focus, leaves full screen or closes, on Ctrl+Alt+Shift, while the shared keyboard and mouse have this keyboard on another computer, and when the window stops answering for a second (a watchdog on the hook's own thread). Ctrl+Alt+Del is Windows' own and never reaches any hook. The window's Send keys menu sends a chord through the same view (the Windows key, Alt+Tab, Alt+F4 and Print Screen, with Task Manager and Windows+L for a Windows one; never Ctrl+Alt+Del, which reboots a Linux computer showing a text console, and never Alt with Print Screen, Linux's magic SysRq) and only while it controls that computer (limit 62). Turn the setting off to keep these keys here.

## Using it safely today

- **Use Tailscale, or another VPN, anywhere you do not trust everyone on the network.** It closes the limits above for traffic between your own devices.
- **Keep `pairing_required = true`.**
- **On a shared network,** turn on "Ask before each session" for your phones, and grant each phone only what it needs.
- **Keep the control and stream ports closed to the internet.** The WAN path (iroh) does not need them open.
- **Pair by scanning the QR code** rather than typing an address. It pins the right computer before the first connection.
