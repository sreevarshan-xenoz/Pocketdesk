# The BG cycle (2026-10-27): connectivity, low latency, uninterrupted streaming

The owner asked for the core remote-desktop experience to get attention: the link, the delay, and a picture that does not freeze. An inventory of the streaming path (capture, encoders, the QUIC transport, the bitrate controller, the phone's decoder, reconnects) found where time goes and where a stream stalls:

- **The phone reads frames in order, one at a time.** Each frame is a reliable QUIC stream, and none is ever given up. One lost packet holds every later frame and the sound until it is resent (`core/src/streaming/client.rs`, the uni-stream loop), and frames a newer keyframe has made moot are still delivered, late.
- **A keyframe asked for is not made** on the Windows hardware encoders or Linux NVENC (the FFmpeg sidecar, `encoder.rs` `request_keyframe`). After a loss, the picture waits up to 2 s for the next scheduled keyframe.
- **A full capture queue drops the newest frame**, so the last change on the screen can wait up to the 1 s resend.
- **The phone never drops a frame it is behind on,** and it looks for decoded output only when it feeds the next frame.
- **Freezes are not measured.** The session record has no stall count or length, no keyframe recovery time, no frames the server trimmed, and no reconnect time, so a change cannot be shown to help.
- **Connectivity:**
  - A dead link takes about 12 s to notice.
  - The home and internet dials are made one after the other.
  - The internet road's QUIC gets none of the home road's congestion, keepalive and timeout settings.
- **Adaptation is slow.** It ticks every 2 s, has no delay signal, and each change rebuilds the encoder (about 400 ms).

Each item is its own PR, unit-tested, with a device check on the OPPO where it can run (sessions over the internet road, since `adb reverse` carries TCP only). Long runs, such as a slow link on the VM or a 10-minute relayed session, wait for several items together. Nothing plays sound. This plan is removed when the cycle ends.

## The measuring stick

`server/tests/lossy_link_smoothness.rs` runs the real server, with a moving test pattern for the screen (`POCKETDESK_TEST_PATTERN`), through the chaos proxy. Baseline on main after BG1 and BG2, this box's NVENC sidecar, 1080p60, 20 Mbit/s, 10 ms each way, 45 s:

| Link | fps | gap p50 / p95 / p99 / max | stalls of 200 ms or more | e2e p50 / p95 / p99 |
|---|---|---|---|---|
| clean | 60.0 | 16 / 24 / 28 / 31 ms | 0 | 28 / 30 / 32 ms |
| 2 % loss | 53.0 | 15 / 56 / 149 / 485 ms | 13 | 29 / 435 / 623 ms |

No freezes on either: a frame is never lost, only late, which is what BG3 is for.

## Moved into the cycle

- **An in-process Windows encoder (BG8).** On Windows every hardware encoder runs as an FFmpeg program fed frames on stdin. It cannot be asked for a keyframe, and each change of rate restarts it (about 500 ms on the OPPO). Building the encoder into the server (FFmpeg's libraries through `ffmpeg-next`, linked with MinGW) is the real fix for both. It starts as a research spike: whether it links and runs here.

## Not in it

- Datagrams with forward error correction instead of streams. That is a larger rework; BG3 gets most of the benefit with the streams there are.
- Audio: its jitter buffer and A/V sync, since anything to do with sound is not tested here.
