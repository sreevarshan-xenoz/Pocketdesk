# Getting Pocketdesk into F-Droid (research, 2026-10-14)

Roadmap item T3. This is the plan for publishing the Android app on F-Droid's main repository: built from source, reproducibly, and signed with the developer's own key. It also covers what was learned about IzzyOnDroid and Google's developer verification. Claims marked *unverified* were not confirmed.

## Two findings that change the plan

1. **IzzyOnDroid is unlikely to accept the app.**
   - Its inclusion policy is "strongly opposed to apps which are fully or in part created by generative AI tools", and it rejects "vibe-coded apps" (<https://izzyondroid.org/docs/general/AppInclusionPolicy/>).
   - Much of this repository was written with AI assistance, and the commits say so in their `Co-Authored-By` trailers.
   - That must not be hidden: the policy also punishes a lack of transparency.
   - F-Droid has no such rule. An interim policy modelled on Debian's ("neither endorses nor prohibits") is proposed (<https://gitlab.com/fdroid/admin/-/work_items/699>), and a reviewer may still raise it (*unverified*).
   - Ways to install without either store: **Obtainium** (installs straight from GitHub releases) or a self-hosted F-Droid repository.
2. **ML Kit was a build blocker, not only a label.**
   - F-Droid's scanner lists `com.google.mlkit` as non-free with no anti-feature, so a build containing it fails.
   - The "bundled" model still shipped a closed native decoder and models.
   - It also pulled in Play services and Firebase components, and sent Google usage data with no opt-out.
   - **Done on branch `feat/fdroid-ready`:** the scanner uses zxing-cpp (Apache-2.0).

## Done (branch `feat/fdroid-ready`)

- **QR decoding with zxing-cpp 3.1.1**, read straight from CameraX frames. An instrumented test on the A71 decodes the desktop app's own QR, dark-on-light and inverted.
- **The APK is arm64 only:** the Rust bridge exists for arm64 alone.
- **No dependency-info block:** F-Droid's and IzzyOnDroid's checks refuse it.
- **Not packaged:** the iroh and iroh-relay cdylibs that cargo-ndk copies next to the bridge.

## Done (branch `feat/fdroid-build`, 2026-10-15)

- **Step 1:** `android/bridge/build-android.sh` with the Rust pin in `android/bridge/rust-toolchain-version` (1.99.0), used by CI and the release workflow. Not a repo-wide `rust-toolchain.toml`: on the Windows dev box it would select the MSVC host, which cannot link there; the script's pin can be overridden for a developer. No path of the building machine is left in the library (checked: the checkout, Cargo's home and the toolchain all mapped).
- **Step 2:** the NDK pinned in `android/bridge/ndk-version` (29.0.14206865), installed exactly by CI through `ANDROID_NDK_HOME` and required by the script in CI; cargo-ndk 4.1.2 `--locked`; JDK 21 in CI. Gradle's `ndkVersion` is not set: the app compiles no native code itself, so the NDK that matters is the bridge's.
- **Step 3:** the release APK is signed with `--alignment-preserved true`: apksigner from build-tools 35 on re-aligns by default with its own padding (here it moved 458 of 474 entries), which no F-Droid build could match. The workflow then checks every entry's place and padding against AGP's unsigned APK, and the 16 KB alignment.
- **Step 4:** the `Reproducible APK` workflow (`.github/workflows/reproducible.yml`) builds the bridge and the unsigned release APK on `ubuntu-24.04` and `ubuntu-22.04`, the source in different folders, and compares them. Its first run (2026-10-15) gave identical bytes on both: the APK (sha256 `397fa3c7…`) and the bridge `.so`, so `baseline.prof` needs no change. It runs again on every change to `android/`, `core/` or `Cargo.lock`. Not yet tried: F-Droid's own buildserver (Debian trixie) through its recipe.
- **Step 5:** `fastlane/metadata/android/en-US/` (title, descriptions, icon, changelog). Screenshots owed.

**Step 1 in detail:**
- `rust-toolchain.toml` pins the channel and adds the Android target.
- The script (`build-android.sh`):
  - cleans `jniLibs`;
  - builds with `--release --locked --platform 26`, with one codegen unit and stripped symbols;
  - sets `RUSTFLAGS="--remap-path-prefix=$ROOT=/pocketdesk --remap-path-prefix=$CARGO_HOME=/cargo -C link-arg=-Wl,--build-id=none"` and a fixed `CARGO_HOME`;
  - copies only the bridge library.

## Open questions

- **zxing-cpp ships prebuilt native libraries in its AAR** (from Maven Central). Binary Eye, already in F-Droid, uses the same AAR, which suggests it is accepted. F-Droid may still ask for it to be built from source (*unverified*).

## Anti-features and policies

| Item | Expected verdict | What to do |
|---|---|---|
| ML Kit, Play services, Firebase | Build blocker plus tracking | **Removed** |
| n0's public relays (iroh) | Probably none: the relay is free software and can be self-hosted (N2), and Syncthing's public relays carry no anti-feature | Say so in the description |
| Mainline DHT | None: it is decentralized (as with LibreTorrent) | Say so in the description |
| Texts (SMS), notification access | Allowed and off by default: KDE Connect has both | Explain both permissions |
| CameraX, local network permission | Fine | — |
| License field | fdroiddata uses one SPDX id | `License: MIT` (the code is MIT or Apache-2.0) |
| `aws-lc-sys` (C) in the bridge's dependency tree, through reqwest, iroh and noq | Free, but C code can embed build paths | Cover it in step 1's path mapping; consider `ring`-only if the libraries allow it (*unverified*) |

## Google's developer verification

- **In force since 2026-09-30** in Brazil, Indonesia, Singapore and Thailand, for installs from Google Play and the major OEM stores, on certified devices.
- **Not covered in this phase:** F-Droid, IzzyOnDroid, browser sideloads and adb.
- **2027:** Google says it expands globally. How F-Droid installs will be treated then is *unverified*.
- **A reason for the developer-signed route:** one registration of the release certificate covers GitHub, Obtainium and F-Droid alike, since F-Droid would publish the developer's own signed APK.
- Sources: <https://developer.android.com/developer-verification> and F-Droid's open letter, <https://f-droid.org/2026/02/24/open-letter-opposing-developer-verification.html>.
